# 2026-08-28:VLM 混合式架構——三輪裝機驗證與退化生成修復

## 背景

延續前一輪確認的方向:Apple Vision OCR 對漫畫手寫粗體字不可靠(實測把
`¡UWA! ¡¡UWAA!!` 認成 `¡LIWA! ¡¡LWAA!!`),但 Vision 的 boundingBox(位置)
可靠、也是「原地回填」唯一的座標來源。改成混合式架構:

- **位置** = Vision OCR 的 boundingBox(繼續用)
- **文字內容** = 不信任 Vision 辨識出的文字,改成把 bbox 對應區域從原圖裁一小塊,
  丟給 MLX 視覺語言模型(Qwen3-VL-4B-Instruct-4bit)直接讀圖 + 翻譯,一次搞定

今天的工作是這個架構落地後的裝機驗證迭代(共三輪回饋 + 一輪修復未驗證)。

## 今天新增/修改的檔案

- `Sources/OCR/RegionCropper.swift`(新增):Vision 正規化座標→像素矩形、往外擴邊(橫 8%/縱 20%)、裁圖、orientation 正規化
- `Sources/OCR/RegionMerger.swift`(新增):合併相鄰/重疊的 Vision bbox 成一顆對話框再裁圖,VLM 呼叫次數減半以上、能看到完整語句上下文
- `Sources/Translation/ImageTranslationEngine.swift`(新增):讀圖翻譯引擎協定,跟既有純文字 `TranslationEngine` 並存
- `Sources/Translation/LanguageNames.swift`(新增):VLM 用的語言代碼→完整名稱對照
- `Sources/Translation/VLMTranslationEngine.swift`(新增):核心實作,`VLMModelFactory` 載入、裁圖轉 CIImage、prompt 設計、warm-up、退化輸出偵測與重試
- `Sources/Overlay/TextBlock.swift`:欄位改用像素座標,加 `recognizedText`(VLM 讀到的原文,跟 Vision 分開存)
- `Sources/ContentView.swift`:pipeline 改成「OCR 定位→合併→逐塊裁圖+VLM(即時更新畫面)」,加引擎切換(VLM / 文字模型+TranslateGemma),除錯清單加裁圖縮圖 + 三欄對照
- `project.yml`:加 `MLXVLM` product

## 測試資料

固定測試圖(`Fixtures/sample-es.jpg`)上 4 個文字區塊(西班牙文→繁中):

1. `¡UWA! ¡¡UWAA!! ¡¡¡UWAAA!!`(頂部驚叫聲)
2. `YA BASTA...`(一般句子)
3. `ERES RUIDOSO..`(一般句子)
4. `¡¡¡GRRRRRRAAAAGH!!!! ¡¡¡AGAAAAAGH!!!`(底部,合併過兩行的怒吼聲)

## 三輪裝機驗證時間軸

**第一次**:混合式架構核心假設成立——`YA BASTA...`/`ERES RUIDOSO..` 這兩句 VLM 讀字正確、翻譯合理(「好了,夠了...」「你是吵鬧的...」)。但發現新問題:貪婪解碼(temperature 0)在難讀的裁圖(1、4 兩個驚叫/怒吼區)上會卡進生成迴圈,輸出變成一長串同一字元重複,燒光 maxTokens 也生不出正常格式。
→ 修法:temperature 0→0.2、maxTokens 128→80、`parse()` 加退化輸出偵測(同一非空白字元連續重複 ≥12 次判定失敗,回傳明確錯誤訊息而非垃圾文字)。

**第二次**:退化偵測生效,頂部區塊正確顯示「[生成失敗:輸出異常重複]」。但底部合併區塊出現新失敗模式——只複誦完 Step 1(原文)就停住,沒寫到 Step 2(翻譯),輸出被截斷在 `ORIGINAL:...`,不是字元重複,退化偵測抓不到。判斷是 maxTokens 80 對「合併過多行、內容較長」的框太緊。
→ 修法:maxTokens 拉回 150。

**第三次**:maxTokens 150 確認解決截斷問題,但生成本身還是卡進重複迴圈,兩個難字區塊(頂部、底部)都被退化偵測抓到,乾淨顯示失敗訊息(不再是截斷半成品)。兩句一般句子維持翻對。
→ 判讀:兩塊失敗案例有共通點——來源文字本身就是大量重複字母(`UWAAA`、`GRRRRRRAAAAGH`)。不想常駐拉高 temperature(會犧牲已經翻對句子的穩定性),改成「只在偵測到退化輸出時,原地重試一次、溫度拉高到 0.7」。

**第四次(重試機制上線後)**:頂部區塊重試後仍然失敗(退化偵測仍然命中)。底部合併區塊這次沒有卡迴圈,但重試输出還是只複誦完原文兩行、沒寫到 `TRANSLATION:`,`parse()` 的 fallback 把整段未完成輸出當譯文顯示出來(畫面上譯文欄變成一串 `ORIGINAL:...` 原始文字,是明顯錯誤的顯示結果)。
→ **根因診斷**:prompt 的 Step 1 要求「重複字母要跟原圖一模一樣、逐字複誦」,對本來就是大量重複字母的狀聲詞等於沒有自然停止點——這才是卡迴圈與「複誦完就沒 token 寫翻譯」兩種失敗模式共同的源頭,不是溫度或 maxTokens 的問題。
→ 修法:把 Step 1 指示改成「重複字母不用精確計數,寫 2-4 次自然的重複量就好,趕快進入 Step 2」。

**第五次(2026-08-31 裝機驗證上一輪修法)**:結果幾乎沒變——頂部區塊依然是完全退化失敗;底部合併區塊 `VLM讀到` 這次抓到完整兩段原文,但 `譯文` 欄還是顯示未完成的 `ORIGINAL:...` 原始輸出,代表模型還是沒能寫到 `TRANSLATION:` 那行。
→ **修正診斷**:上一輪判斷「措辭要求精確複誦」是根因,裝機驗證證明不是(或不是全部)——真正的結構性問題是**順序**:prompt 要求先寫 Step 1(讀原文)再寫 Step 2(翻譯),只要模型在複誦原文階段卡住/耗光額度,排在後面的翻譯就永遠生不出來,不管措辭怎麼放寬都一樣。
→ 修法:**把輸出順序整個對調**——Step 1 改成先要求 TRANSLATION,Step 2 才是 ORIGINAL(僅供除錯參考)。這樣即使模型在寫原文時卡住,真正需要的譯文已經在那之前寫出來了。`parse()` 本來就是逐行找標籤、不假設順序,不用改動。

**第六次(裝機驗證順序對調)**:**這次改動是負分**。頂部區塊這次總算把原文讀對了(`VLM讀到:¡UWA! ¡¡UWA!! ¡¡¡UWAAA!!!`,不再是 Vision 認錯的 LIWA),但 `TRANSLATION` 欄卻原封不動照抄原文,完全沒有翻譯動作。更嚴重的是連續五輪都穩定翻對的 `YA BASTA...`/`ERES RUIDOSO..` 這次也被搞壞——前者輸出被截斷成 `TRANSLA...`,後者譯文欄混進原文黏成一團。
→ **教訓**:先讀原文再翻譯這個「兩步驟」本身在幫一般句子維持翻譯品質,問題只出在兩個重複字母極端多的難字上,不該為了救這兩個難字動到對所有區塊都生效的主要 prompt。
→ 修法:**改回原本驗證過穩定的 ORIGINAL→TRANSLATION 順序**(等於還原第四次之前的版本),兩個難字改交給 retry 階段一個**完全不同、更簡化**的 prompt 處理——retry prompt 直接拿掉「逐字讀出原文」這一步(那正是卡迴圈的根源),只要求「給一個自然的音譯,不用對照原文」,只輸出一行 `TRANSLATION:`。主要 prompt 完全不受影響,退化偵測命中才會換到這個 retry prompt。**這輪還沒裝機驗證。**

**第七次(裝機驗證第六輪的還原+簡化 retry prompt)**:`YA BASTA...`/`ERES RUIDOSO..` 確認恢復穩定(還原主要 prompt 順序有效)。但兩個難字**兩塊都還是判定為「輸出異常重複」**——代表簡化 retry prompt(拿掉讀原文步驟)本身沒能解決問題,retry 溫度 0.7 仍然卡迴圈。

回頭比對第六輪(順序對調)的原始資料:那一輪頂部難字用的是**主要 prompt、temperature 0.2**,是目前為止唯一一次在這塊難字上生出乾淨、不卡迴圈輸出的紀錄(雖然翻譯內容錯了,照抄原文,但沒有卡進字元重複)。反觀每一次用 **0.7** 重試(不管 prompt 內容),兩塊難字都卡迴圈。這跟「拉高溫度打散貪婪路徑」的直覺相反——證據顯示對這顆 4-bit 小模型,0.7 在這種輸入上比 0.2 更容易卡迴圈,不是更不容易。
→ 修法:retry 溫度從 0.7 改回 0.2(跟主要 prompt 同溫度),只靠「拿掉讀原文步驟、縮短生成長度」這個變因降低卡迴圈機率,不再依賴拉高溫度。

**關鍵轉折(Cyril 提出的對照組)**:七輪都在同一張緊裁圖上換 prompt/溫度都沒解決,Cyril 指出一個關鍵事實——同樣的模型(Qwen3.5/Gemma4)透過手機上的 Locally AI **看整張原圖**就能正確讀出這兩塊難字,不是模型本身讀不懂。真正的差異其實是**我們裁太緊**:VLM 只看到孤立的一小塊字,沒有分鏡/對話框的上下文,這比溫度或措辭更可能是卡生成迴圈的根因,而七輪測試從沒動過「給模型看多大範圍」這個變因。

→ 修法(架構性,不是再猜 prompt 措辭):`ImageTranslationEngine` 協定新增 `widerContext: CGImage?` 參數。主要路線不變(緊裁圖 + 已驗證穩定的 prompt/溫度),只有退化偵測命中時,retry 才換成**同一位置但擴邊範圍大很多的裁圖**(寬 150%/高 400%,約略涵蓋整個對話框/分鏡),搭配拉高的縮放目標(768→1024,補償擴大的範圍避免目標文字反而更模糊)+ 簡化 prompt(提醒模型「這張圖有其他上下文,只翻譯那句喊叫」)。`ContentView.runVisionPipeline` 用 `RegionCropper.padded` 多算一次寬裁圖傳進去。**這輪還沒裝機驗證,是目前為止第一次真正改動「retry 用的圖」而不是只改 prompt/溫度。**

- 穩定翻對:`YA BASTA...`、`ERES RUIDOSO..`(2/4 區塊,六輪測試都正確,只有第六輪因為改動主要 prompt 被波及,已還原)
