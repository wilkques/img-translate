# 2026-09-02:WKWebView 圖片偵測骨架(第一輪風險驗證,vault session 落地)

## 背景

Cyril 在 vault 端(另一個 Jarvis session)討論「像看網漫一樣即時翻譯」的體驗,查證後發現這就是本專案 README 一直排在「下一步(這次不做)」的 WKWebView 整合。vault 端規劃了完整整合的架構,但明確標出兩個未驗證、可能讓整條路線不可行的假設,建議先花一輪裝機驗證這兩點,再投入完整整合。這輪的工作就是把「第一輪風險驗證」的程式碼落地。

## 兩個要驗證的假設

1. 原生端 `URLSession` 帶 cookie+Referer 下載網頁圖片,抓不抓得到真的圖(很多站靠這個防盜鏈)
2. JS 偵測到的圖片網址是不是已經是 lazy-load 換好的真實網址,不是 `data-src` 占位字串

## 這輪新增的檔案

- `Sources/WebReader/PageBridge.swift`:注入用的 JS(字串常數,不是資源檔——避免 XcodeGen 對 `.js` 資源檔處理方式的不確定性)。`IntersectionObserver` 提前 2 個螢幕高度偵測 + `MutationObserver` 盯屬性變化(lazy-load)與節點新增(無限捲動動態插入圖片)
- `Sources/WebReader/MangaWebView.swift`:`UIViewRepresentable` 包 `WKWebView`,`WKUserScript` 掛在 config 上換頁自動重新注入
- `Sources/WebReader/TranslationRequestCoordinator.swift`:`WKScriptMessageHandler` 收圖片網址 → 同步 cookie(`HTTPCookie.requestHeaderFields`)+ Referer 下載 → 結果存進 `@Published probes` 給畫面顯示。含 `WeakScriptMessageHandler` 避免 `WKUserContentController.add(_:name:)` 造成的強引用循環
- `Sources/WebReader/MangaReaderView.swift`:網址列 + WebView + 除錯清單(偵測到/下載中/成功 bytes+尺寸/失敗原因)
- `ImgTranslateApp.swift`:改成 `TabView`,「閱讀」(新)+「引擎測試」(原本的 `ContentView`)並存
- `project.yml`:`dependencies` 加 `sdk: WebKit.framework`

## 刻意沒做的事

- 沒接翻譯 pipeline(`TextRecognizer`/`VLMTranslationEngine` 完全沒被這輪程式碼呼叫)
- 沒做疊字回填 DOM(`imgTranslateApplyOverlay` 之類的注入函式還沒寫)
- 沒做序列化處理佇列(這輪還沒有東西需要排隊,只有下載+解碼)
- 沒動 ATS(`Info.plist` 的 `NSAppTransportSecurity`)——如果裝機測試發現 HTTP 網站載入失敗,才需要考慮加例外,不要在還不知道要不要的情況下先放寬安全設定

## 第二輪:接翻譯 pipeline + 疊字回填 DOM(還沒裝機驗證)

Cyril 確認先鎖定同一個網站測試,不用先擴大測別的站,直接進第二輪。

### 改動

- `Sources/WebReader/PageBridge.swift`:
  - 新增 `ensureWrapped(img)`——**只在圖片通過 `isCandidate` 準備要回報時才包一層 `position:relative` 的 wrapper**,不是無條件對頁面上每個 `<img>` 都包(小圖示/廣告/頭像不會被動到,縮小對原站版面的干擾範圍)
  - 新增全域函式 `window.imgTranslateApplyOverlay(elementId, blocks)`:依 `data-imgtranslate-id` 找回圖片,清掉舊的疊字 `.imgtranslate-block`,依每個 block 的百分比(`left`/`top`/`width`/`height`,跟 Vision 的 0-1 正規化座標系一致)畫半透明底色塊+譯文,字級用 wrapper 目前的 `clientHeight` 換算成像素動態決定
- `Sources/WebReader/TranslationRequestCoordinator.swift`:
  - 圖片下載成功後不再只顯示 bytes/尺寸,改成丟進**序列化佇列**(`pendingJobs` + `isProcessingQueue`)排隊跑翻譯——同時間只有一個推理在跑,跟 `ContentView` 對 VLM 引擎的限制一致
  - 翻譯邏輯**照抄** `ContentView.runVisionPagePipeline` 的整頁對位演算法(`vlmEngine.translatePage` → 用 `PageOutputParser.fold`/`similarity` 逐項比對相似度、過門檻才採用 → 沒對到的區塊退回 `vlmEngine.translateRegion` 逐塊翻譯),不是重新設計——`Sources/OCR/*`、`Sources/Translation/*` 一行都沒改
  - 翻譯完成後把每個區塊的 pixelRect 換算成相對圖片的百分比 + 譯文,組成 JSON,用 `webView.evaluateJavaScript` 呼叫 `imgTranslateApplyOverlay` 回填
  - `ImageProbe.Status` 擴充成 `detected/downloading/translating/translated(blockCount)/noTextFound/failed`,除錯清單能看出卡在哪一步
- `Sources/WebReader/MangaReaderView.swift`:
  - 加語言選單(跟 `ContentView` 同一份清單,`Picker` 綁 `coordinator.sourceLanguage`/`targetLanguage`)
  - 加 VLM 引擎狀態列(下載進度/暖機/翻譯中,樣式抄 `ContentView.vlmEngineStatusLine`)
  - 這個畫面自己養一份 `VLMTranslationEngine`(`init()` 裡建立,注入進 `coordinator`),**跟「引擎測試」分頁是兩個獨立實例**——已知限制,見下方

### 已知限制,這輪刻意沒處理

- **兩個分頁各自一份 VLM 引擎**:平常只用其中一個分頁沒問題,但如果兩邊在同一個 session 裡都觸發翻譯,可能同時各載入一份 3GB+ 模型。要修的話要把引擎持有者上移到 `ImgTranslateApp` 層級共用,牽動 `ContentView` 既有結構,這輪先不做,等真的遇到問題再處理
- **DOM wrapper 可能干擾版面**:`ensureWrapped` 把 `<img>` 包進一層新 `div`,對一般 block/flow 排版通常沒事,但如果原站用 `display:flex`/`grid` 且該 `<img>` 是直接子元素,包一層可能打亂版面(wrapper 變成新的 flex/grid item,不會自動繼承原本 `<img>` 該有的 flex/grid 屬性)。這個測試網站是不是這種版面還不知道,要裝機看疊字後版面正不正常
- **字級/排版沒有真正的漫畫字體**,跟 `BubbleOverlayView`(原生疊字那條線)目前的視覺調校程度不是同一個水準,這輪先求「疊得上去、看得懂」,排版細節之後再調
- **佇列狀態顯示有落差**:圖片下載完、還在排隊等 VLM 輪到時,除錯清單仍顯示「下載中」,不是新加一個「排隊中」狀態——不影響功能,只是狀態文字不夠精確

### 下次裝機驗證要看

1. 同一個西班牙文漫畫網站,捲動頁面,圖片有沒有依序從 🌀 變成 ✅(疊字 N 個區塊)
2. 疊字视覺效果:位置對不對齊原文框、有沒有把版面弄亂(尤其如果這站是 flex/grid 排版)、字級看不看得清楚
3. 捲動速度快過翻譯速度時,畫面是不是優雅降級(還沒翻完的圖顯示原文,不會卡住/白畫面)
4. VLM 引擎狀態列有沒有正確顯示下載/暖機/翻譯進度(這是這個模型第一次在「閱讀」分頁被觸發載入,理論上跟「引擎測試」分頁行為一致,但引擎是不同實例,要重新走一次下載流程)

## 崩潰修正:2026-09-01 的背景下載實驗 confirmed 是風險 (c)

裝機測第二輪(在「閱讀」分頁第一次觸發 `vlmEngine.translatePage` → `ensureLoaded()` → 下載模型)時崩潰:

```
Completion handler blocks are not supported in background sessions. Use a delegate instead.
```

呼叫堆疊落在 `HuggingFace.HTTPClient.performFetch` → `HubClient.downloadSnapshot` → `HubSnapshotDownloader.download` → `VLMTranslationEngine.ensureLoaded`。這正是 `notes/2026-09-01.md`「補上背景下載」那段自己預告的三種風險之一(c):`HubClient`(`swift-huggingface`)內部用了完成處理常式(completion handler)風格的 API,iOS 明確禁止在背景 `URLSessionConfiguration` 上使用,執行期直接丟例外,編譯期抓不到。當時的應變方案就是「revert,改用 `beginBackgroundTask`」,這輪照做:

- `LocalModelStore.makeHubClient()`:`URLSessionConfiguration.background(withIdentifier:)` 改回 `.default`,拿掉 `sessionSendsLaunchEvents`/`isDiscretionary`/自訂 `delegate` 這些只有背景 session 才有意義的設定
- 刪除 `BackgroundSessionDelegate`(`LocalModelStore.swift`)、`Sources/AppDelegate.swift`,`ImgTranslateApp.swift` 拿掉 `@UIApplicationDelegateAdaptor`——這套機制存在的唯一理由就是背景 session 的生命週期合約,session 不再是背景的之後全部變成死碼,清乾淨不留著
- `VLMTranslationEngine.ensureLoaded()`/`LocalLLMTranslationEngine.ensureLoaded()` 都加上 `beginBackgroundTask`/`endBackgroundTask` 包住整個下載+載入流程——**這不是解法,是緩解**:只延長切背景瞬間的一點點前景執行時間(系統給的額度通常幾十秒到幾分鐘,不保證撐完 2-3GB 下載),使用者中途切背景下載仍可能中斷,但至少不會像現在這樣直接崩潰

**這輪還沒裝機驗證修正結果**,下次測試除了原本第二輪要看的疊字效果,還要確認:模型下載能不能正常跑完(不再崩潰)、全程保持在前景操作。

## 第二個崩潰:兩個分頁各自默默載入一份 3GB+ 模型,OOM

上面那個修好、重新裝機測,Cyril 這次沒看到程式碼崩潰的 log,只回報「開始翻譯會閃退」,附上的是系統低記憶體快照(bug_type 298,jetsam)不是我們程式碼的例外堆疊。快照顯示當下系統剩餘記憶體不到 100MB,且 `LiveContainer` 進程出現多筆、其中一筆 rpages 換算約 6.8GB。Cyril 確認沒有同時開其他 App、也確認測的是修過崩潰的新版本。

**根因**:`ImgTranslateApp.swift` 的 `TabView` 兩個分頁都是直接寫在 `TabView { ... }` 裡,SwiftUI 的 `TabView` 預設會把**所有分頁的畫面都建出來**,不是只建目前選中的那個分頁。`ContentView`(引擎測試分頁)有 `.task(id:...)` 會在畫面一出現就自動對內建測試圖跑一次翻譯 pipeline,這個 `.task` 在 `TabView` 初始化時就被觸發了——不需要使用者手動點進那個分頁。也就是說使用者人在「閱讀」分頁操作,`ContentView` 已經在背景默默下載/載入了**第二份**跟「閱讀」分頁完全獨立的 3GB+ VLM 模型(這正是這份改動 08/02 那份 notes 裡標成「已知限制」的那一點,但當時低估了它的觸發條件——以為要使用者「兩邊都手動用」才會踩到,實際上只要兩個分頁同時存在於畫面樹裡就會自動觸發)。兩份模型疊起來,記憶體直接被推爆到系統要用 jetsam 清記憶體的程度。

**修法**:`ImgTranslateApp.swift` 新增 `RootTabView`,`TabView(selection:)` 搭配 `if selection == .reader { MangaReaderView() }` 這種寫法,**沒被選到的分頁完全不進入視圖樹**,`.task` 自然不會被觸發,兩個分頁的引擎就不可能同時常駐記憶體。`ContentView`/`MangaReaderView` 內部程式碼一行都沒動,只改了 App 入口這一層怎麼組裝兩個分頁。

**代價(刻意接受的取捨)**:切出「引擎測試」或「閱讀」分頁再切回去,該分頁的 `@StateObject`(含 VLM 引擎)會被整個銷毀重建——等於要重新載入一次模型權重進記憶體(不是重新下載,`LocalModelStore` 的檔案快取還在,只是重新讀檔+暖機那幾秒到十幾秒),而且「閱讀」分頁的 WebView 瀏覽狀態(目前看到哪一頁、捲動位置)切出去再切回來也會重置。這個代價換來的是不會再兩份模型同時吃記憶體。

**這輪還沒裝機驗證**,下次測試:全程只用「閱讀」分頁(不要點進「引擎測試」分頁),看記憶體壓力/閃退問題是不是真的解決;之後如果要驗證「引擎測試」分頁本身,記得先切離「閱讀」分頁(或接受兩者不能同時停留在有模型載入的狀態)。

## 暫時整個隱藏「引擎測試」分頁

Cyril 要求先把「引擎測試」畫面整個藏起來,專心測「閱讀」這條主線,不要留任何雙模型風險。改法:`ImgTranslateApp.swift` 拿掉 `TabView`,直接顯示 `MangaReaderView()`。`ContentView.swift`(以及它牽涉到的 `LocalLLMTranslationEngine`/文字引擎那條路線)**沒有刪除**,檔案還在、還會被編譯,只是現在整個 App 沒有任何地方建立 `ContentView` 的實例——沒有實例就不會有 `.task` 被觸發,自然不可能再載入第二份模型。之後要恢復「引擎測試」分頁,參考 git 歷史 `6b872dd` 那個 commit 的 `RootTabView` 寫法換回去即可,`ContentView` 本身完全沒受影響。

## 第三個崩潰:單一模型連續處理多張圖,記憶體隨推理次數累積

雙模型問題排除後重新裝機測,這次**確認翻譯 pipeline 真的成功運作了**——Cyril 截圖顯示 App Switcher 上的最後畫面:「視覺模型就緒」,`0.webp` 疊字成功 7 個區塊、`0_1.webp` 疊字成功 2 個區塊(兩者都顯示 ✅),閃退發生在處理第 3、4 張圖(`01_01.webp` 翻譯中 / `01_02.webp` 下載中)的時候。這次系統設定裡沒有找到對應的分析紀錄(可能是 jetsam 事件沒有生成使用者看得到的報告,或還沒同步)。

**判讀**:前兩張撐過去、之後才炸,型態是「連續推理次數累積」而不是單一固定觸發點的 bug。查 `TranslationRequestCoordinator.runTranslation`,`vlmEngine.finishPage()`(內部呼叫 `MLX.Memory.clearCache()`)原本**只在整張圖處理完的最後呼叫一次**——如果一張圖裡有好幾個區塊需要逐塊 fallback(`0.webp` 就疊了 7 個區塊,很可能不只一個要走 fallback),等於好幾次推理疊在一起都還沒清過快取。

`VLMTranslationEngine.finishPage()` 原本的既有註解特別交代「不要每塊都叫,會逼 MLX 重新配置緩衝區,反而更慢」——但那個結論是針對 `ContentView`「一次只處理一張固定測試圖」這個情境算出來的,跟閱讀分頁「一個 session 要連續處理不限張數的網頁圖」完全是不同的使用模式,舊的假設不能直接套用過來。

**修法(實驗性)**:`runTranslation` 的逐塊 fallback 迴圈裡,**每處理完一個區塊就呼叫一次 `finishPage()`**,不是等整張圖處理完才清一次。用推理速度換穩定性。這輪還沒裝機驗證,下次測試重點:
1. 崩潰問題是不是真的解決(能不能連續捲過 4 張圖以上不再閃退)
2. 翻譯速度有沒有明顯變慢到不能接受的程度——如果穩定性有改善但速度太差,下一步考慮折衷(例如每 2-3 個區塊清一次,而不是每一個)
3. 如果這次還是崩潰,麻煩務必想辦法找到崩潰當下的記錄(設定裡的分析資料可能需要幾分鐘才會同步出現,或裝置重開機一次再查),沒有堆疊資訊很難再往下精準定位

## 第四輪:抓到真正的 JetsamEvent,確認是記憶體上限問題

逐塊清快取那版裝機重測,閃退位置幾乎沒變(還是卡在第 2、3 張圖之間)。這次 Cyril 直接抓到 `JetsamEvent-2026-09-02-120505.ips`(不是快照,是系統實際觸發砍 App 的那次事件記錄),關鍵欄位:

```
"name": "LiveContainer",   ← LiveContainer 執行 guest App 的方式,這其實就是 ImgTranslate 自己
"states": ["active", "frontmost"],
"rpages": 395916,          ← 換算約 6.2GB
"reason": "per-process-limit",
```

**確認結論**:這不是我們哪一行程式碼寫錯,是 App 本身的常駐記憶體(`Qwen3-VL-4B` 模型 3.2GB + Vision OCR + 圖片解碼 + MLX 推理暫存張量,連續處理好幾張網頁圖累積下來)直接頂到 LiveContainer 側載環境的 per-process 記憶體上限(`lc-memprobe` 當初測出來大約 6GB)。逐塊清快取那個實驗性修法方向沒錯但不夠——快取有清,但模型本身固定佔用的 3.2GB 加上其他開銷,總量還是會在處理幾張圖後逼近天花板,不是清快取頻率能解決的。

**修法**:`MangaReaderView` 預設模型從 `Qwen3-VL-4B`(約 3.2GB)換成選單裡最小的 `Qwen3-VL-2B`(約 1.78GB),多留將近 1.5GB 空間。同時把模型選單(含下載/移除按鈕)加到這個畫面——原本只有「引擎測試」分頁才有,「閱讀」分頁完全沒地方換模型,現在可以直接裝機比較不同模型在「連續處理多張圖」這個新情境下撐不撐得住,不用重新編譯。選單用自訂 `Binding` 呼叫 `vlmEngine.changeModel(to:)`(照抄 `ContentView.enginePicker` 的寫法),不能直接綁 `$vlmEngine.selectedModel`——直接綁會跳過「換模型前要先卸載舊模型」的保護,可能意外造成新舊模型同時佔記憶體,在這輪本來就在追記憶體問題的情境下格外不能犯這個錯。

**這輪還沒裝機驗證**,下次測試:
1. 用最小的 `Qwen3-VL-2B` 能不能連續捲過 4-5 張圖以上不崩潰
2. 如果 2B 穩定但翻譯品質明顯太差,再用選單試中間的 `Qwen2.5-VL-3B`,在穩定性與品質之間找平衡點
3. 逐塊清快取那個實驗性修法予以保留(沒有壞處,只是這輪發現它不是主因)

## 裝機結果:2B 穩定但翻譯內容不對,3B 出現「兩個原文疊出同一句譯文」

**`Qwen3-VL-2B`**:裝機確認四張圖全部 ✅ 疊字成功(7+2+4+5 個區塊),記憶體上限問題解決、沒有再崩潰。但疊字內容(`YABASTA...`/`ERES RULDOSO...`)看起來是原文或音譯,不是真的翻成繁中——小模型指令遵循能力不夠,翻譯品質這個取捨在裝機上得到驗證。

**切到 `Qwen2.5-VL-3B`** 重測:Cyril 回報「翻譯似乎不正確」——`YA BASTA`跟`ERES RUIDOSO`(兩句意思完全不同的原文)疊出來的譯文**一模一樣**都是「哇哇哇...」。這比「翻得不夠準」更可疑,懷疑是配對邏輯把不同區塊的譯文配錯,或模型把兩句都誤讀成同一種喊叫聲——但當時的除錯清單只顯示「疊字 N 個區塊」的成功筆數,看不到每個區塊實際讀到/翻到什麼,無法判斷是哪一種。

**補上除錯明細**:`TranslationRequestCoordinator` 新增 `BlockDebug`(Vision 辨識文字/VLM 讀到/譯文/來源),整頁對位成功、逐塊 fallback 成功時都各自記一筆,存進 `ImageProbe.blocks`。`MangaReaderView` 的除錯清單改成可展開(`DisclosureGroup`),點開每張圖能看到逐區塊明細,樣式照抄 `ContentView` 既有的除錯清單寫法。

**下次裝機**:同樣的網址、同樣切 `Qwen2.5-VL-3B` 重跑一次,這次展開「哇哇哇...」那兩個區塊的明細,看:
1. 兩者的「來源」是不是都顯示「整頁(分數 X.XX)」——如果分數偏低卻還是配上了,是門檻或對位邏輯要調
2. 兩者的「Vision 辨識」欄位(來自我們自己的 OCR,不會因為 VLM 換模型而變)是不是本來就正確顯示兩句不同原文——如果 Vision 沒錯但配對配到同一個 VLM 輸出項目,問題在對位;如果 VLM 讀到/譯文兩欄本身就重複,問題在模型輸出本身重複(小模型常見的生成迴圈/重複輸出)

## 抓到真正根因:parser 假設兩行分開,Qwen2.5-VL-3B 擠成一行

裝機展開明細,四個區塊全部顯示「來源:逐塊(整頁沒對到)」,第 3 筆「VLM讀到」欄位洩漏關鍵線索:`YA BASTA...TRANSLATION:ya basta...`——`ORIGINAL:` 跟 `TRANSLATION:` 被模型擠在**同一行**,沒有換行。

`VLMTranslationEngine.parse()`/`PageOutputParser.parse()` 都是逐行比對、只認「行首」的 `ORIGINAL:`/`TRANSLATION:`(這個假設是照 `Qwen3-VL-4B` 穩定輸出兩行的習慣寫的)。擠在同一行時,整行被 `ORIGINAL:` 的 anchored 比對整段吃掉,`translated` 永遠抓不到值:
- 在 `PageOutputParser` 這層,`translated` 空字串 → `isDegenerate = true` → 這個項目在整頁對位迴圈裡直接被跳過,**連判斷像不像都沒機會**——這就是為什麼整頁VLM對這張圖完全沒對到任何一塊,四塊全部落到逐塊備援
- 在逐塊備援自己的 `VLMTranslationEngine.parse()` 這層,同樣的擠行問題讓 `translated` 抓不到值 → 判定「生成失敗」→ 觸發 retry
- retry 用的 `makeRetryPrompt` 是寫死問「這裡有一聲喊叫,給音譯」的專用 prompt——一旦所有正常輸出都被誤判失敗、全部落到這條路線,不管原文是什麼,retry 都只會回一個通用喊叫音譯,四句完全不同的原文因此疊出同一句「哇哇哇」

**修法**:兩個 parser 的 `ORIGINAL` 分支都加一段——抓到的內容裡如果混進了 `TRANSLATION:` 標記,就地切開,前半段是原文、後半段是譯文,不必等下一行。這是既有 `Sources/Translation/*` 的真正邏輯漏洞(不是新模型的問題,是舊 parser 的格式假設只覆蓋了 `Qwen3-VL-4B` 一種輸出習慣),破例修這裡,不算違背「這輪不動 Translation 核心」的原則,因為這是真的 bug 不是重新設計。

**修完還沒裝機驗證**,下次測試:
1. 這個 bug 修好後,`Qwen2.5-VL-3B` 的四個區塊是不是不再全部變成同一句「哇哇哇」,`來源`欄位有沒有機會顯示「整頁」而不是全部落到「逐塊」
2. 就算 parsing 修好,翻譯**內容品質**本身還是要另外看——`YA BASTA...TRANSLATION:ya basta...` 這個例子裡,模型只是把原文小寫複誦一次,根本沒有真的翻成中文,這是小模型指令遵循能力的另一個獨立問題,parsing bug 修好不代表翻譯品質就達標

**裝機結果**:parsing bug 確認修好——四個區塊不再是同一句,喊叫聲那塊甚至靠整頁對位翻對(「啊啊啊」,分數 0.67)。但 `ERES RUIDOSO...`(一句普通句子,不是喊叫)還是掉進「哇哇哇」:這句退回逐塊備援後主要路線判定失敗,觸發 `makeRetryPrompt`——那段 prompt 寫死「這裡一定有一聲喊叫,給音譯」,對普通句子文不對題,吐出跟原文完全對不上的通用喊叫音譯。`YA BASTA...` 那句則是模型直接照抄原文小寫,根本沒翻譯,retry 沒被觸發但翻譯品質本身不合格。

## 評估:回頭衝 4B 不划算,retry prompt 放寬

跟 Cyril 對齊過三個槓桿的實測效果:逐塊清快取有幫助但不夠(`4B` 配這個還是在第 3 張圖左右 OOM)、換小模型才是真正解決 OOM 的關鍵、調小 prefetch 範圍對這次的 OOM 幫助有限(問題是單張圖處理時的推理累積,不是排隊圖片太多)。結論:`4B` 要在連續閱讀場景穩定,得挖出「模型固定佔用之外還有什麼在累積」,這是全新且沒把握的工程,現階段不追;留在 `3B`,修 retry prompt 這個明確可以改善的邏輯問題。

**修法**:`makeRetryPrompt`(`VLMTranslationEngine.swift`)原本寫死「這裡一定有一聲喊叫,給音譯」,改成「可能是普通句子、也可能是喊叫,兩種都給合理翻譯」——保留「如果是喊叫就音譯」的指示,不拿掉這條(這是當初救 `4B`「UWA」難字的關鍵),只是不再預設一律當喊叫處理。

**已知風險,需要重新裝機驗證兩條路線**:
1. 這輪的目標——`3B` 用「閱讀」分頁重跑同一個網址,`ERES RUIDOSO...` 這類普通句子退回逐塊備援時,是不是真的給出合理翻譯而不是通用喊叫音譯
2. 這段 prompt 之前為了 `4B` 的「UWA」難字裝機調了七八輪,措辭很敏感——之後要把「引擎測試」分頁重新接回來(目前整個隱藏著)裝機驗證一次固定測試圖,確認「UWA」難字沒有因為這次改動被拖累退步。這步暫時排在後面,先把「閱讀」這條主線的普通句子問題驗證過

**裝機結果**:retry prompt 修法確認生效——`ERES RUIDOSO...` 這次退回逐塊備援後翻對了(「你是吵鬧的...」),喊叫聲那塊也翻對(「哎呀呀呀」,整頁對到,分數 0.67)。剩下 `YA BASTA...` 還是照抄小寫沒翻譯,但這次「來源」不是通用喊叫音譯,代表根本沒觸發 retry(主要路線判定輸出有效,只是模型自己選擇不翻)——這是純模型能力隨機性,不是邏輯 bug,很難再靠改 prompt 精準解決。三句真對白裡兩句翻對、一句沒翻,比之前「四句全部同一句垃圾」好非常多,Cyril 判斷已經算堪用水準。

## 拚品質:換回 4B + 每張圖處理完整個卸載模型

Cyril 要求繼續拚翻譯品質(「讓他翻對」),不只滿足於堪用。既然逐塊清快取清不動模型容器本身常駐的記憶體,換一個更重的手段:**每張圖處理完就整個卸載模型**,不是只清快取。下一張圖開始翻譯時 `ensureLoaded()` 偵測到 `container` 是 nil 會重新載入,強制把記憶體歸零到跟剛啟動時一樣的基準。

**改動**:
- `MangaReaderView` 預設模型改回 `Qwen3-VL-4B`(拿掉 2B 的覆寫)
- `TranslationRequestCoordinator.runTranslation` 新增 `unloadEngineForNextImage()`,在每張圖處理完(不管成功或「OCR 找到文字但翻譯全部失敗」)都呼叫一次 `vlmEngine.unload()`

**代價**:每張圖之間會多一段重新載入權重+暖機的延遲(模型檔案已經在本機,不用重新下載,但讀檔+編譯 Metal pipeline 還是要花時間,`vlmEngineStatusLine` 既有的下載/載入/暖機階段顯示不用改就能自然呈現這段過程)。

**這是實驗性做法,還沒裝機驗證**,下次測試重點:
1. 用 `4B` 連續處理多張圖,記憶體上限問題是不是真的解決(不再閃退)——如果還是崩,代表除了模型容器本身,還有別的地方在累積,「整個卸載」這個假設也要被推翻
2. 重新載入的延遲有多長、能不能接受——如果每張圖都要等十幾秒以上,使用體驗會很差,可能要考慮拉長卸載週期(例如每 2-3 張圖才卸載一次)
3. `4B` 的翻譯品質是不是真的比 `3B` 好上一截,值得付出這個延遲代價

## 裝機結果:新的當機(Metal 競態),收回整個卸載模型的做法

Cyril 抓到 `LiveContainer-2026-09-02-151836.ips`——這次是**真正的例外崩潰**(`bug_type: 309`,`SIGABRT`),不是靜默被系統砍掉的 jetsam 快照,跟原本追的 OOM 是不同性質的問題。崩潰堆疊卡在:

```
com.Metal.CompletionQueueDispatch 佇列
-[_MTLCommandBuffer didCompleteWithStartTime:endTime:error:]
→ __cxa_throw(例外沒被接住)→ terminate → abort()
```

**判讀**:「每張圖處理完就整個卸載模型」這個做法本身引入了新的競態——卸載動作發生的時候,前一張圖某個 GPU 運算的非同步完成回呼可能還沒真正跑完,模型容器被拆掉後 Metal 偵測到不一致狀態直接丟例外。這比原本的記憶體上限問題更難處理,牽涉到 MLX/Metal 內部的非同步生命週期管理,不是這個層級能安全排時序的問題,继续深挖投入報酬率低。

**收回這個實驗**:
- `TranslationRequestCoordinator.runTranslation` 移除 `unloadEngineForNextImage()` 呼叫與整個函式,不再每張圖卸載模型
- `MangaReaderView` 預設模型從 `Qwen3-VL-4B` 改回固定 `Qwen2.5-VL-3B`——retry prompt 放寬後翻譯品質已經算堪用(見上一節裝機結果:三句真對白兩句翻對),且不會動到模型容器生命週期,沒有這次發現的額外當機風險

**目前定案的閱讀分頁配置**:`Qwen2.5-VL-3B` + 放寬過的 retry prompt + 逐塊清快取(`finishPage()` 保留,對 3B 這個大小的模型是有效的緩解)。`4B` 的路線這輪先關閉,不是完全排除,只是現階段沒有安全的做法讓它撐過連續閱讀場景,之後如果有新線索(例如查出 Metal 競態真正的觸發條件、或 mlx-swift-lm 上游有相關修正)可以再重新評估。

## 重新盤點可用模型:補上先前漏查的兩個架構

Cyril 要求把「還有沒有更好的模型」查徹底。第一輪盤點只看了 `Qwen VL`/`Gemma`/`SmolVLM`/`PaliGemma`,漏掉 `mlx-swift-lm` 原始碼裡實際存在的另外兩個架構實作:`FastVLM.swift`(Apple 自己的)與 `LFM2VL.swift`(Liquid AI)。補查後的完整結論:

**能被 `mlx-swift-lm` 載入的架構**:`qwen2_vl`/`qwen2_5_vl`/`qwen3_vl`/`paligemma`/`gemma3`/`idefics3`/`smolvlm`/`pixtral`/`mistral3`/`fastvlm`/`lfm2vl`。`MiniCPM-V`、`InternVL`、`Moondream` 這些常被稱讚 OCR 準的輕量 VLM **完全沒有 Swift 實作**,要用只能改走 `llama.cpp`(需要自己刻 ObjC++ 橋接 `mtmd_` C API,官方 iOS 框架只開放文字推論),工程量等同重寫推論層,已評估後排除。

**逐一評估後排除的候選**:
- `SmolVLM2-2.2B`:設計目標是省資源/跑影片,不是翻譯品質,評測普遍弱於 `Qwen2.5-VL-3B`
- `SmolVLM-Instruct`(465M)、`Qwen2-VL-2B`:太小或太舊,不會比現況好
- `PaliGemma-3B`:只有 8-bit 版(約 3GB+,一樣撞上限),且是視覺問答基礎模型,沒有指令/翻譯調校
- Apple `FastVLM-1.5B`:強項是「快」(FastViTHD 視覺編碼器效率),語言骨幹是老一代 `Qwen2-1.5B`,翻譯品質大機率不如現況
- `Ministral`:純文字模型無讀圖能力;`mistral3` 架構對應的 `Mistral Small 3` 是 24B 級別,遠超記憶體上限

**新增的兩個候選(這次加進選單)**:
1. **`Gemma 3 4B`**(`VLMRegistry.gemma3_4B_qat_4bit`)——2026 評測顯示 `Gemma 3` 在翻譯/多語言上比 `Qwen3-VL` 系列強(涵蓋 140+ 語言);跟 `Gemma 4` 不同代架構,不會踩到 3.31.4 那個 k_norm 載入 bug。**已知風險**:體積跟會 OOM 的 `Qwen3-VL-4B` 同級,大機率一樣撞記憶體上限,是純品質比較用的選項
2. **`LFM2.5-VL-3B`**(Liquid AI,2026/08 釋出)——28 項視覺評測平均 69.4,追平 `InternVL-3.5-4B`、只落後 `Qwen3.5-4B` 0.7 分,用 3B 體積打出接近 4B 品質;支援 16 語言,改版重點就是多語言視覺理解+指令遵循(正對應我們「叫它翻譯卻照抄原文」的痛點);官方 day-one 出 MLX 格式。加了 4-bit/8-bit 兩個變體,**三個未知數**見 `VLMTranslationEngine.VLMModelOption` 的註解:4-bit repo id 是推測的(只確認 8-bit 存在)、8-bit 約 3.3GB 失去體積優勢、`LFM2.5` 新骨幹能不能被 3.31.4 的 `LFM2VL.swift` 載入未知

**另外發現一個零成本、不用改程式碼的實驗**:Cyril 表示簡體中文也可接受。目標語言選單本來就有「簡體中文」(`zh-Hans` → `Simplified Chinese`,`LanguageNames.swift` 已有對照),現有 build 直接切就能測。推測有效的理由:`Qwen` 系列是阿里巴巴做的,中文訓練資料以簡體為主,一直要求輸出繁體等於在翻譯之外多壓一層它不擅長的字體轉換,可能正是它乾脆照抄原文/格式跑掉的原因之一。**這個要先測**,如果切簡體就改善,可能根本不需要換模型。

**這輪還沒裝機驗證**,測試順序建議:
1. 先用現有 build 把目標語言切「簡體中文」重跑,零成本
2. 新 build 出來後,選單試 `Gemma 3 4B` 與 `LFM2.5-VL-3B (4bit)`,重點看翻譯內容是不是真的翻成中文而不是照抄
3. `LFM2.5` 兩個變體如果下載階段就報 404,代表 4-bit repo id 猜錯,改用 8-bit;如果載入階段報「key not found」之類的錯,代表跟 `Gemma 4` 同一類上游套件還沒支援的問題,不是我們能修的
