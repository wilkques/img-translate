# 2026-09-01:簡化整頁 prompt——結構卡點解決,浮現翻譯行重複的新卡點

## 背景

8/31 收工時卡在一個問題:整頁路線第九輪裝機驗證,整頁輸出只解析出 1 項就整批
退回逐塊,原本以為是頂部難字卡進複誦原文的迴圈燒光額度,但展開實際的「整頁原始
輸出」截圖後發現完全不是這樣——模型一開始就吐出 `BLOCK 0 0 0 0 0 0...`,連第一塊
的 `ORIGINAL:` 都沒寫到,是卡在「要不要寫編號」這個結構層面,連圖片內容都還沒開始
處理。等於 8/31 筆記想驗證的「模型看到多大範圍的圖能不能讀懂難字」這個主假設,
根本還沒被真正測到。

診斷:整頁 prompt(`makePagePrompt`)比已驗證穩定的逐塊 prompt 複雜得多——要模型
自己估計「大約幾塊文字」、按閱讀順序排序、每塊兩步驟、遵守三條規則、還要自己生成
遞增的 `BLOCK n` 編號並判斷何時停止列舉。這種複合式指令很可能超出這顆 4-bit 小
模型的指令遵循能力,在最開頭的「數字/編號」決策點就先卡死。

## 這輪做了什麼

只改 `Sources/Translation/VLMTranslationEngine.swift` 的 `makePagePrompt`,拿掉
兩個結構性複雜度來源,只留下已證實必要的兩條防卡迴圈硬規則:

1. **拿掉「roughly N text areas」的數量提示**——最可疑的觸發點,`approximateBlockCount`
   參數整個從 prompt 文字裡移除(呼叫端算 `pageItemLimit` 用的 `expectedBlockCount`
   不受影響,那是另一條路徑)
2. **拿掉要求模型自己生成遞增 `BLOCK n` 編號的輸出格式**,改成純粹重複
   `ORIGINAL:`/`TRANSLATION:` 兩行,不用改 `PageOutputParser`——它本來就設計成
   `BLOCK` 行可有可無,遇到第二個 `ORIGINAL:` 就隱含換下一項
3. 保留「同一字母不准連續超過 4 次」「太難讀就寫 `ORIGINAL: ?` 但仍要給出最佳
   TRANSLATION,不要停在難的那個」這兩條規則,措辭不動
4. Step 1/Step 2 兩步驟結構、ORIGINAL→TRANSLATION 順序、狀聲詞音譯指示,全部照抄
   逐塊路線已驗證有效的措辭,不重新發明

刻意只動這一個變因(prompt 結構複雜度),`PageOutputParser`、逐塊路線的
`makePrompt`/`makeRetryPrompt`、`ContentView` 的對位邏輯全部不動。

## 裝機驗證結果

整頁原始輸出(550 字):

```
BLOCK 1
BLOCK 1
ORIGINAL: ¡LUWA! ¡¡LUWAA!!! ¡¡¡LUWAAA!!!
TRANSLATION: 啊!啊啊啊啊啊啊啊啊啊啊...(一路重複「啊」到 550 字上限)
```

**結構卡點確認解決**:不再卡進「連內容都沒開始讀」的 `BLOCK 0 0 0 0...` 迴圈。這次
模型真的讀了圖,`ORIGINAL` 讀出 `¡LUWA! ¡¡LUWAA!!! ¡¡¡LUWAAA!!!`,比 Vision 認的
`¡LIWA! ¡¡LWAA!!` 更接近真實文字(雖然多了個 L 開頭沒完全讀對,但明顯是在讀圖,不
是在卡結構)。而且模型自己主動寫了兩次 `BLOCK 1`——新版 prompt 已經沒要求編號,
代表這是模型自己的輸出習慣,不是被 prompt 誘發的;解析器本來就容忍這種情況。

**新問題,範圍更窄更明確**:`TRANSLATION` 這一行違反了「同一字母不准連續超過 4
次」這條硬規則——模型翻譯這個難字(狀聲詞)時卡進「啊」的重複迴圈,一路吐到把
整頁 512 token 的額度全部燒光在**這一塊的翻譯**上,導致後面 BLOCK 2/3/4
(`YA BASTA`、`ERES RUIDOSO`、`GRRRAAAGH`)完全沒機會被列出來。整頁只解析出 2 項
(一項是重複 `BLOCK 1` 行造成的空項),跟 Vision 4 塊對不上,還是整批退回逐塊。

**關鍵差異**:同一條「不准連續超過 4 次」規則,模型在 `ORIGINAL` 那行遵守了,在
`TRANSLATION` 那行完全沒遵守——生成中文疊字翻譯比生成拉丁字母原文更容易卡迴圈。
這跟 8/31 筆記記錄的逐塊路線 `GRRRAAAGH` 案例是同一種失敗模式(讀對但翻譯重複
失控),差別是**整頁模式下這個失控會吃光全頁的生成額度、拖累其他三塊**——逐塊
模式下最多只拖累那一塊自己的 150 token,不會波及別塊。

## 下一步

「模型看到多大範圍的圖能不能讀懂難字」這個主假設**還是沒有被完整驗證到**——這次
連讀圖本身都成功了(`ORIGINAL` 讀對大半),卡點已經收斂到單一變因:**翻譯難字時的
輸出長度控制**。候選方向:

- 把「不准連續超過 4 次」這條規則講得更明確針對 TRANSLATION 行(目前規則寫「in any
  line」,但實測對翻譯行沒有約束力,可能要用更強的措辭或範例示範)
- 串流中途偵測到單一項目卡進重複迴圈就提前截斷,強制跳到下一個 `ORIGINAL:`/
  `BLOCK`,不要讓一塊拖垮整頁額度(8/31 筆記已提過這個方向,還沒實作)
- 幫整頁生成的 `TRANSLATION` 加一個字數/token 軟上限提示(例如「每塊翻譯不超過
  15 個字」),減少單塊失控時的最大傷害範圍
- 評估風險已知的 `repetitionPenalty` 參數(GitHub issue #258 提到某些模型首次生成
  會 crash,目前刻意避開,可能要重新評估)

四個方向中選了風險最低、跟這次方法論最一致的第一個(純 prompt 措辭,不動架構/
邏輯,一次只動一個變因)——串流中途截斷跟 `repetitionPenalty` 工程量/風險都更高,
留到 prompt-only 方向試過還是沒用時再上。

## 第二次改動:加強 TRANSLATION 行的重複限制

`makePagePrompt` 的 Rules 區塊原本只有一條「同一字母不准連續超過 4 次,in any
line」,實測對 `ORIGINAL` 行有效、對 `TRANSLATION` 行沒有約束力——模型讀原文時有
「照抄圖上筆畫」這個具體錨點,翻譯時沒有等效的停止訊號。改動:

1. 規則拆成兩條,新增一條**專門針對 TRANSLATION** 的規則,明講「這條規則對翻譯行
   一樣嚴格適用」,並給出具體的短範例(`啊啊啊` 而不是長串)
2. 加一個**字數上限**當第二道防線:「每則 TRANSLATION 控制在約 15 字以內」——就算
   模型還是不遵守「不准連續超過 4 次」,字數上限至少能把單一區塊失控時吃掉的額度
   限制在小範圍,不會拖垮整頁其他區塊
3. `TRANSLATION` 的格式範例本身也加了「kept short」/「as a short burst」提示,呼應
   Rules 的要求

只改文字,`PageOutputParser`、逐塊路線、`ContentView` 完全不動。**這輪還沒裝機
驗證。** 下次測試要看:整頁原始輸出裡頂部難字的 `TRANSLATION` 行是不是真的變短了
(不再燒光整頁額度),以及這次整頁輸出能不能列出全部 4 塊、對位成功。

## 第二次改動裝機驗證:新失敗模式,可重現兩次

裝機後沒有出現預期的「翻譯行變短」,而是完全不同、更嚴重的失敗——**模型把 prompt
的說明文字整段複誦回來**,不是在生成內容。

第一次:
```
ORIGINAL: <text>
TRANSLATION: <translation>
¡LUWA! ¡¡LUWAA!!!  ¡¡¡LUWAAA!!!  YA BASTA...  ERES RUIDOSO...  ...(四塊內容
無標籤裸列,還重複列兩次)...啊啊啊!啊啊啊…(尾端又燒光額度)
```

第二次(要求原地重測同一版本,確認是否重現):**幾乎整段 prompt 說明文字被逐字
複誦**,包含 placeholder 括號內容、完整 Rules 清單、結尾的 `Output ORIGINAL/
TRANSLATION pairs...` 那句,只有語言名稱被正確替換成「Traditional Chinese」
(代表不是字面複製 prompt 模板,是生成過程「續寫」了近似的說明文字)。**兩次都
出現類似的照抄現象,確認可重現,不是抽樣雜訊**。

### 診斷:三輪長度/結果對照,收斂到「prompt 總指令量」

| 輪次 | 相對長度 | 結果 |
|---|---|---|
| 8/31 原版(數量提示+BLOCK 編號+兩步驟) | 最長 | `BLOCK 0 0 0...`,連讀圖都沒開始 |
| 第一次改動(拿掉編號+數量提示) | 223 字/1,196 字元(最短) | 有讀圖,翻譯卡重複迴圈 |
| 第二次改動(加長 placeholder+多兩條 Rules) | 274 字/1,485 字元(最長) | 整段照抄 prompt 說明文字 |

「變短=進展、變長=退步」三輪一致,不管拉長的是編號要求還是規則說明。**根因收斂
到「prompt 總指令量超出這顆 4-bit 小模型的負荷上限」,不是任何單一措辭寫法的
問題。**

### 第三次改動

把整頁 prompt 結構重新對齊已驗證穩定的逐塊 prompt(`makePrompt`)寫法:
- 語意說明(標點保留、不修正成真實單字、狀聲詞要音譯)搬回 Step 1/Step 2 的
  敘述句裡,不再塞進 `<...>` placeholder
- placeholder 恢復成極短版:`<the text you read>`/`<the \(target) text>`,跟
  逐塊 prompt 完全一致——放進句子裡的說明文字是「指示」,放進括號的 placeholder
  才是模型該模仿的「輸出範例格式」,兩者混在一起可能是模型分不清「這是要遵守的
  規則」還是「這是我該寫的內容」而複誦整段的原因
- 三條 TRANSLATION 相關規則合併回一條(防重複、適用範圍、字數上限三合一)

改動後字數 263 字/1,400 字元——**比第一次改動的版本還是長一截(只比第二次改動
短 6%),不是原本設想的「貼近第一次改動版本」**。這代表這次不保證解決問題:如果
實際觸發門檻落在 1,196~1,400 字元之間,這次可能還是複誦。但無論結果如何都是有用
的數據點——複誦重現就能坐實「長度是關鍵」且門檻低於 1,400 字元;不複誦就能把
安全範圍縮小到 1,196~1,400 字元之間。

**這輪裝機驗證**:「照抄 prompt 說明文字」這個新退化模式沒有再出現,證實結構性
修法有效(即使字數還是比第一次改動版本長,關鍵確實是「語意說明有沒有混進
placeholder」而不是純字數)。但退回到第一次改動版本就有的老問題——翻譯難字時卡進
「啊啊啊」重複迴圈,燒光整頁 512 token 額度,只解析出 1 項,還是整批退回逐塊。
合併成一條的 TRANSLATION 防重複規則,對這個難字第二次被證明沒有約束力。純
prompt 措辭這條路對「控制翻譯輸出長度」大概已經到頂,如果要繼續解決這個問題,
下一步要嘛做架構性的串流中途截斷,要嘛接受整頁路線目前搞不定這兩個難字。

## 轉向:逐塊路線的寬裁圖 retry 從未被真正觸發過(bug)

使用者提出一個問題——逐塊路線對頂部難字是不是「每次都變成 LIWA」?查證後這是
誤會:`Vision:` 那行顯示的 `¡LIWA! ¡¡LWAA!!` 是 Apple Vision OCR 的基準參考(從
沒變過,跟 prompt 改動無關),不是 VLM 自己的輸出——`VLM讀到:` 欄位每次都是
`¡¡¡`,不是 LIWA。但這個釐清的過程意外挖出一個更重要的發現。

**查證除錯清單顯示邏輯時發現:寬裁圖 retry 機制(8/28 第四輪設計來救這兩個難字)
對頂部 UWA 這塊,實際上從來沒有被觸發過。** 除錯清單只有在 `usedWiderContextRetry`
為真時才會顯示「↻ 已走寬裁圖重試」橘字標記,但所有截圖裡這塊從來沒出現過這個
標記——查 `VLMTranslationEngine.parse()`(第 404-441 行)才發現是一個邏輯 bug:

主要 prompt 對這塊的原始輸出通常是 `ORIGINAL: ¡¡¡¡¡¡¡...(157字)`——卡在複誦
原文階段,完全沒寫到 `TRANSLATION:`。這種情況下 `parse()` 原本的邏輯:
1. 解析出 `original` 有值(那串 `¡`),`translated` 是空字串(沒有 TRANSLATION 行)
2. `translated.isEmpty` 成立,進入 fallback:把**整段原始輸出(含 `"ORIGINAL:"`
   標籤字樣)**當成 `translated` 候補
3. 收斂重複後變成 `"ORIGINAL: ¡¡¡"`
4. `hasUsableContent()` 只檢查有沒有任一字母/數字——`"ORIGINAL"` 這幾個字母讓它
   誤判「有內容」,回傳 `true`
5. 函式不回傳 `failureMessage`,而是把 `"ORIGINAL: ¡¡¡"` 當正常譯文回傳
6. `translateRegion` 的重試判斷條件 `firstAttempt.translatedText == failureMessage`
   永遠不成立,retry 從未執行

### 修法

`parse()` 的 fallback 條件加上 `&& original.isEmpty`——只有在模型**完全沒照格式
輸出**(`original`、`translated` 都是空的,整段裸寫一般文字)時才適用「整段原始
輸出當譯文」這個 fallback。`original` 有解析到值但 `translated` 沒有,代表模型
卡在讀原文階段,`translated` 要保持空字串,讓 `hasUsableContent` 正確判定失敗、
真正觸發寬裁圖 retry。改動範圍小(一個條件式),不影響 `YA BASTA`/`ERES RUIDOSO`
穩定案例(那兩塊 `translated` 從解析迴圈就有值,不會進到這個 fallback 分支)。

**這輪裝機驗證**:bug 修法生效,寬裁圖 retry 第一次真的被觸發——除錯清單出現
「↻ 已走寬裁圖重試」橘字標記跟橘框縮圖,「第1次原始輸出」跟「重試原始輸出」也
第一次都有資料。但**實際結果是還是沒救到**:重試原始輸出跟第一次一樣,整段是
純 `¡` 符號的重複迴圈(150字),完全沒讀到任何內容。

對照組:同一塊文字在**整頁路線**(給模型看整張頁面)至少讀出了實質內容
(`¡LUWA! ¡¡LUWAA!!! ¡¡¡LUWAAA!!!`,雖不完全正確但遠比純符號有內容)。這代表
「範圍越大越有幫助」這個趨勢可能還成立,只是逐塊 retry 目前擴邊範圍(1.5/4.0)
還不夠寬,離整頁路線的範圍有落差。

## 除錯清單 UI 整理

四塊區塊同時展開(2 張縮圖+最多 6 行文字)裝機截圖畫面爆版,難以判讀。把
`debugList`(`ContentView.swift`)每列包成 `DisclosureGroup`(沿用 `pageDebugSection`
既有寫法),預設只顯示 Vision/VLM讀到/譯文/來源摘要,縮圖、重試標記、兩次原始
輸出移進展開內容。純 UI 調整,不影響任何翻譯邏輯。

## 逐塊 retry 寬裁圖擴邊拉大

把 `padFractionX: 1.5, padFractionY: 4.0, minPadPixels: 60` 拉大到
`padFractionX: 2.5, padFractionY: 6.0, minPadPixels: 80`(`ContentView.swift`
兩處呼叫點,`runVisionPipeline` 與整頁路線的逐塊 fallback,原本就是重複邏輯,
一起改)。

**已知風險,還沒解開**:`RegionCropper.padded()` 最後會用 `.intersection(bounds)`
夾回頁面邊界。頂部 UWA 這塊本來就貼著頁面最上緣,往上擴邊的部分可能提早被夾掉,
實際擴大的效果不保證跟倍數成正比——如果這塊的寬裁圖本來就已經被邊界夾到接近
整頁高度,單純加大倍數對它可能是無效改動。

**裝機驗證,風險成真**:橘框縮圖範圍跟前一輪(1.5/4.0)幾乎沒變,兩次原始輸出
字數也完全相同(157字/150字,一字不差)——證實邊界夾限確實先擋住了,倍數從
4.0 拉到 6.0 對這塊是無效改動。**除錯清單也順便整理過**:`ContentView.swift`
的 `debugList` 每列改包成 `DisclosureGroup`(沿用 `pageDebugSection` 既有寫法),
預設只顯示 Vision/VLM讀到/譯文/來源摘要,縮圖跟原始輸出移進展開內容,四塊同時
攤開的畫面爆版問題解決。

### 改用整頁圖當 retry 輸入

靠倍數擴邊逼近整頁範圍這條路確認走不通(邊界夾限先擋住)。改成 `ContentView`
兩處呼叫點(`runVisionPipeline`、整頁路線的逐塊 fallback)的 `widerCrop` 直接
用 `page.cgImage`(整頁原圖),不再透過 `RegionCropper.padded()` 算擴邊矩形。

這是目前為止最乾淨的對照實驗:整頁路線已經證明模型看整張頁面時,這塊文字至少
讀得到實質內容(`¡LUWA! ¡¡LUWAA!!!`)。如果 retry 用整頁圖還是吐純 `¡` 符號,
代表差異不在「看多寬」,是整頁 prompt(`makePagePrompt`)跟 retry prompt
(`makeRetryPrompt`)的措辭差異——「範圍是關鍵」這個從 8/28 就開始追的主假設
該被推翻,要往別的方向查(prompt 措辭,或接受這塊救不回來、走雲端 fallback)。

刻意沒動 `makeRetryPrompt` 的文字(仍描述「a panel...shown with extra
surrounding context」)——這輪只改「retry 看到多大的圖」這一個變因,不要同時
動 prompt 措辭,才能乾淨判斷結果差異的原因。

**裝機驗證**:橘框縮圖確認換成整頁原圖了,但重試原始輸出還是純 `¡` 符號
(共150字)——**跟前兩輪擴邊倍數調整時的結果一模一樣**。「範圍是關鍵」這個從
8/28 追到現在的主假設,到這裡可以判定被推翻:retry 現在看到的圖跟整頁路線
完全相同,同一張圖在整頁路線至少讀出了實質內容,逐塊 retry 卻整段空轉,差異
必然不在圖片範圍。

### 下一個變因:retry 的 maxTokens

三輪的「重試原始輸出」字數都精準卡在「(共150字)」,推測是撞到 `retryParameters`
的 `maxTokens: 150` 上限,不是真的「輸出剛好都是150個字」這麼巧——如果模型一
開始生成就卡進重複,150 token 的額度可能撐不到它脫離卡頓,整頁路線的
`maxTokens: 512` 才有機會撐過去。retry prompt 其實比整頁 prompt 簡單(只要求
一行 TRANSLATION,不用列 ORIGINAL),照理該更容易成功,結果卻更差,額度不夠
很可能是原因。把 `retryParameters.maxTokens` 從 150 拉到 512,對齊整頁路線,
單獨測試這個變因,prompt 跟圖片範圍都不動。

**裝機驗證,假設推翻,而且有副作用**:重試原始輸出這次精準卡在新上限「共512字」
——跟「150」時代精準卡在150 是同一個模式,證實模型從頭到尾沒有要脫離迴圈的
跡象,不是「差一點撐不過去」,額度大小根本不是這塊的瓶頸。

更嚴重的是,同一輪測試裡 `YA BASTA...`(十幾輪來第一次)、`GRRRAAAGH` 的譯文都
跟著跑掉/失常(`YA BASTA` 直接顯示生成失敗,`GRRRAAAGH` 譯文變成「哼哼哼！
（咆哮）！！！」)。裝機重跑同一張測試圖在「maxTokens 還是 150」的舊版本
(`17a0335`)上,這兩塊立刻恢復穩定(「停了啦...」「呀啊啊啊」)——坐實這不是
抽樣雜訊,是拉高 maxTokens 的副作用:頂部那塊的重試生成時間拉長很多(512 token
的空轉),推測拖累了同一輪後續區塊的生成穩定性。**改回 150**,不留這個沒有好處
還有代價的改動(`f3eb121`)。

### 目前收斂:範圍、額度兩個假設都被推翻

- **範圍假設(8/28 起的主假設)**:retry 用整頁圖跟裁圖範圍逼近整頁,結果都一樣
  失敗,已推翻
- **額度假設**:maxTokens 512 vs 150,輸出都精準卡在各自上限,模型沒有要脫離
  迴圈的跡象,已推翻,而且有副作用

剩下還沒測過的變因:**prompt 本身的措辭/結構**。retry prompt(`makeRetryPrompt`)
只要求一行 `TRANSLATION`,整頁 prompt(`makePagePrompt`)要求列出全部文字並且是
`ORIGINAL`→`TRANSLATION` 兩步驟——兩者現在用的圖、額度都已經對齊,結果卻天差
地遠,差異只剩 prompt 寫法本身。下一輪如果要繼續查,方向是比對兩份 prompt 的
具體差異,或考慮接受這塊救不回來、轉向雲端 fallback。

## 整頁對位放寬:數量不符不再整批放棄

使用者發現一件事:整頁路線這幾輪測試「整頁輸出 1 項 / Vision 定位 4 塊」時,
雖然數量不符整批退回逐塊,但那唯一解析出來的第 1 項其實對應到頂部 UWA 那塊,
內容(`ORIGINAL: ¡LUWA! ¡¡LUWAA!!!...`)跟 Vision 認的 `¡LIWA! ¡¡LWAA!!` 相似度
早在 8/31 就算過是 ≈0.59,遠高於門檻 0.3——這代表舊邏輯連「其實對得上」的內容
都一起丟掉了。

**舊邏輯**(`ContentView.swift`):`pageResult.items.count == blocks.count` 完全
相符才進比對迴圈,按位置配對(`items[i]` ↔ `blocks[i]`),數量不符就整批放棄,
不做任何比對。

**新邏輯**:拿掉數量相符的硬性前提。不管解析出幾項,每一項都跟**還沒配到的**
Vision 區塊逐一算相似度,分數最高且過門檻(`PageOutputParser.similarity` +
`fold`,現有的 `pageMatchThreshold`)才配對,配到的區塊標記已使用避免重複配對。
沒被任何項目配到的區塊照舊退回逐塊。

**為什麼這不是新的猜測性邏輯**:「數量相符」情況下原本也不是直接信任位置——
每一對都還是要通過相似度門檻才會採用,位置只是原本配對的起點線索。這次只是把
同一個既有的安全網(相似度門檻),套用到數量不符的部分結果上,沒有降低把關
標準,只是不再因為「整頁沒能一次列滿全部區塊」就連好的部分一起放棄。

除錯清單的提示文字同步更新(「整批退回逐塊」→「逐項比對相似度,過門檻才
採用」),避免跟新行為矛盾。

**裝機驗證**:對位放寬邏輯本身行為正確——但這輪整頁生成又用另一種方式失敗,
沒能真正測到「放寬對位能不能救回部分正確結果」這件事。整頁原始輸出這次只有
73 字:
```
ORIGINAL: <the text you read>
TRANSLATION: <the Traditional Chinese text>
```
模型把 `makePagePrompt` 裡刻意改到最精簡的 placeholder(`79f485a` 那輪的修法)
**原封不動照抄出來**,完全沒填入真實內容——是「照抄 prompt」問題的第三種變體
(第一次照抄一大段完整說明文字,這次照抄的是最精簡的兩行範例格式),規模小很多
但本質相同。因為這項內容是垃圾,跟任何 Vision 區塊的相似度都過不了門檻,放寬
後的對位邏輯正確地沒有勉強配對——安全網有效,只是這次沒有可用的內容可以救。

### 整頁路線階段性小結

從 8/31 開始到現在,整頁路線連續多輪、至少四種不同的失敗模式(結構卡死→翻譯
卡重複→完整照抄→精簡照抄),没有一次乾淨成功過。逐塊路線這邊,頂部 UWA 這塊
從 8/28 起也已經嘗試了範圍擴邊、整頁圖 retry、額度調整,全部無效。這塊難字
前後累積投入遠超過 15 輪裝機測試。

### 決定:不接雲端 fallback

跟使用者討論過雲端 LLM fallback 的具體做法(觸發時機、API 選擇、key 存放、
Gemini API 有免費層可能夠用等)。**使用者決定不採用**——目標是維持整個 app
完全免費、不依賴任何第三方服務,不想承擔免費額度政策未來可能改變、或圖片被
送到第三方伺服器的隱私取捨。**這條路線關閉,之後不用再重新考慮。**

### 目前狀態(當時以為要收工,後來又開了新方向,見下)

- `YA BASTA...`、`ERES RUIDOSO..`:穩定翻對,逐塊路線
- `GRRRAAAGH`(底部吼叫):穩定翻對(`呀啊啊啊`),collapseRepeats 修法生效
- 頂部 UWA 驚叫聲:仍然無法翻譯,整頁與逐塊路線都試過多種變因,全部無效,
  雲端備案已排除。等於目前架構下這塊文字暫時是已知的天花板——**但這個天花板
  只針對 Qwen3-VL-4B-Instruct-4bit 這一顆模型**,見下一節。
