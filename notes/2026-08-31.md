# 2026-08-31:改成「整頁讀圖翻譯」——座標仍由 Vision 提供

## 為什麼改架構

到前一輪為止,兩個極端狀聲詞區塊(`¡UWA! ¡¡UWAA!!`、`¡¡¡GRRRRRRAAAAGH!!!!`)已經連續**八輪**修不好,而八輪動的都是同兩類變因:

- prompt 措辭 / 輸出順序(放寬重複字母要求、TRANSLATION 排到 ORIGINAL 前面、簡化的 retry-only prompt)
- 生成參數(temperature 0 → 0.2 → 0.7、maxTokens 128 → 80 → 150)

其中「輸出順序對調」那輪還是負分:兩個難字沒救到,反而把原本穩定翻對的 `YA BASTA...`/`ERES RUIDOSO..` 搞壞(輸出截斷、譯文跟原文黏在一起),已還原。

**決定性證據來自 Cyril 的對照組**:他用手機上的 Locally AI,以 **Gemma 4 (E2B,約 2B 有效參數)** 與 **Qwen3.5 (4B)** 讀同一段我們一直失敗的文字,兩顆都正確讀出。這兩顆跟我們用的 Qwen3-VL-4B-Instruct-4bit **同級或更小**——所以「模型容量/量化不夠」這個假設被直接推翻。

唯一真正的差別:**Locally AI 看的是整張圖,我們餵給模型的是一小塊孤立裁圖,沒有任何分鏡或對話框的上下文。**「模型看到多大範圍」是八輪下來從沒被動過的變因。

## 這輪做了什麼

整頁一次呼叫 → 模型依閱讀順序列出頁面上所有文字(原文 + 譯文)→ 依順序配回 Vision 的 bbox → 沒配到的區塊自動退回逐塊路線。

座標依然完全來自 Vision(最終產品要對網頁 `<img src>` 原地回填,座標不能丟),模型只負責「讀到什麼、翻成什麼」。

### 新增檔案

- `Sources/Translation/ImagePageTranslation.swift`:`PageTextItem` / `ImagePageTranslation` 純資料型別,刻意不含座標
- `Sources/Translation/PageOutputParser.swift`:整頁輸出解析 + 對位工具
  - 刻意做成**獨立的 free-standing `enum`**,不掛在 `@MainActor` 的 `VLMTranslationEngine` 上——先前兩次編譯失敗都踩在「nonisolated 情境呼叫 MainActor-isolated static」,獨立型別沒有 isolation 可繼承,結構上不可能再犯
  - 刻意**不做串流增量解析**,整段收完再解析(`maxTokens` 本身就是上界),少一層狀態機 = 少一類沒有本機編譯器抓不到的錯
  - `isDegenerateLine` 逐**行**判斷退化,不可以拿整段判:整頁輸出裡出現「啊啊啊啊…」這種正常的中文疊字譯文很合理,整段門檻會誤殺整頁結果

### 修改

- `ImageTranslationEngine`:新增 `translatePage(...)`(帶預設實作回傳 `nil`),`translateRegion` 完全不動
- `VLMTranslationEngine`:新增整頁路線。既有的 `makePrompt`/`makeRetryPrompt`/`parse`/`generateParameters`/`retryParameters`/`translateRegion`/warm-up **全部原封不動**——這是「不可以把已經好的兩塊搞壞」的保證
- `RegionMerger`:合併結果補上閱讀順序排序(順序對位的硬前提,順帶讓除錯清單由上到下排,截圖好判讀)
- `TextBlock`:新增 `source`(整頁/逐塊)、`matchedItemIndex`、`matchScore`
- `ContentView`:引擎選單改三選一(整頁VLM / 逐塊VLM / 文字模型)、新增 `runVisionPagePipeline`、除錯清單每列加「來源」行、新增頁層級除錯區段

### 關鍵設計決定

**對位要求數量完全相符才做**,數量不符就整批退回逐塊,不做任何猜測性對位。理由:Vision 的 bbox 是回填唯一依據,把譯文綁到錯的框會變成「看起來成功、其實是錯的」沉默失敗——那比明確失敗更難發現、代價更高(每輪驗證要一次 CI + 裝機)。

**對位正規化會把連續重複字元收成一個**(`fold`)。這步是關鍵:prompt 要求模型只寫 2-4 次重複,Vision 讀到的卻是原圖實際次數,不收斂永遠配不上。手算驗證:

| Vision(可能認錯) | 模型正確讀出 | fold 後 | Dice 相似度 |
|---|---|---|---|
| `¡LIWA! ¡¡LWAA!! ¡¡UWAAA!!!!` | `¡UWA! ¡¡UWAA!! ¡¡¡UWAAA!!!` | `liwalwauwa` vs `uwauwauwa` | ≈ 0.59 |
| `¡¡¡GRRRRRRAAAAGH!!!! ¡¡¡AGAAAAAGH!!!` | 同段(≤4 次重複) | 兩邊都是 `graghagagh` | 1.00 |
| `YA BASTA...` | `YA BASTA...` | `yabasta` | 1.00 |

門檻起手值 0.3,三個案例都遠高於門檻;實際分數會印在除錯清單每一列上,等裝機數據再校準。

**prompt 刻意不塞 Vision 的 OCR 文字當提示**(那樣對位會變簡單)。那會重新引入混合式架構要避開的污染——模型會錨定在 `¡LIWA!` 上複製 Vision 的錯誤,正是先前翻出「離哇」的成因。Vision 文字只在事後當對位訊號。

**prompt 三個針對實測失敗模式的設計**:
1. 「同一個字母不准連續超過 4 次」放獨立 Rules 區塊當硬規則(第五輪證明埋在步驟裡的軟措辭沒用)
2. 「太難讀就寫 `ORIGINAL: ?` 然後跳下一塊,不要停在難的那個」——卡迴圈的根源就是重複字母沒有自然停止點,這給一個明確的逃生口
3. `BLOCK n` 分隔給模型「後面還有別塊要列」的前進壓力(單獨面對一塊 `UWAAAAA…` 時完全沒有前進壓力),同時給解析器明確的項目邊界

**解析度**:`sample-es.jpg` 是 589×1145,長邊 fit 1024 → 527×1024,只縮 0.89 倍,幾乎原生。視覺 token 約 530,**比現在四次逐塊呼叫的總和還便宜**。`MediaProcessing.apply()` 用 `bestFitScale = min(tw/W, th/H)`,所以超長條漫傳非正方形目標(1024×3072)等於「寬度 fit + 高度上限」,避免長邊 fit 把寬度壓到字糊掉。

## 下一步(裝機驗證)

Push → CI 編譯 → 裝機 → 選「整頁VLM」→ 截圖。一張截圖要回答三個問題:

1. **整頁原始輸出裡有沒有正確的 `¡UWA! ¡¡UWAA!!` 與 `GRRRAAAGH`?** → 直接證實或推翻「上下文才是關鍵」這個核心假設,**而且與對位成功與否無關**
2. **四列的「來源」是不是都顯示「整頁」?分數多少?** → 對位有沒有成功、門檻該不該調
3. 若 (1) 是、(2) 否 → 下一輪只需要修對位(加序列對位 DP,或用 Set-of-Mark 在整頁上畫框標記目標區塊,只跑沒配到的少數區塊)。若 (1) 否 → 上下文假設被推翻,改走雲端 LLM fallback(Cyril 已提出的備案)

另外對照:切到「逐塊VLM」確認 `YA BASTA...`/`ERES RUIDOSO..` 仍然翻對(回歸測試,同一顆 build 不用重編)。
