# 2026-09-03:本機翻不出來時,退而求其次用 Google 翻譯(文字限定)

## 背景與範圍(重要:這是紅線的例外,不是推翻)

這個專案從一開始的紅線是「完全不接雲端服務,圖片不上傳第三方伺服器」,理由是隱私+免費。Cyril 這次主動要求「如果翻不出來 就用 google 翻譯」,問清楚範圍後拍板:

- **只送文字,不送圖片**——只在本機 VLM(含它自己內部的寬裁圖重試,見 `VLMTranslationEngine.translateRegion` 的 `maxWiderContextRetries`)最終仍判定失敗時才觸發
- 用 **Google 翻譯網頁版底層的免費公開端點**(`translate_a/single?client=gtx`),不是要申請 key 的官方 Cloud Translation API——先試最簡單的,之後真的被擋再考慮換

## 新增/修改的檔案

- 新增 `Sources/Translation/GoogleTranslateFallback.swift`:單一函式 `translate(_:from:to:)`,組 GET 請求打 `translate.googleapis.com/translate_a/single`,解析那個不規則巢狀 JSON 陣列拿翻譯文字。內部語言代碼跟 Google 的代碼在中文上對不上(`zh-Hans`→`zh-CN`、`zh-Hant(-TW)`→`zh-TW`),做了一個小對照表轉換,其餘語言(es/en/ja/ko/fr/de)代碼一致直接透傳。任何失敗(網路、格式解析、空結果)都回傳 `nil`,不丟例外、不讓 App 卡住。
- `Sources/WebReader/TranslationRequestCoordinator.swift` 的逐塊 fallback 迴圈:原本 `result.translatedText == VLMTranslationEngine.failureMessage` 就直接記一筆失敗、`continue`。現在改成:失敗時**優先送 VLM 讀到的 `recognizedText`**(VLM 有讀到字但翻譯步驟失敗的情況),VLM 連讀都讀不出來(`recognizedText` 空)才退而求其次送 Vision OCR 的 `visionText`。呼叫 `GoogleTranslateFallback.translate` 成功就用它的結果疊字,`來源` 標記改成「逐塊,Google 翻譯備援」,方便在除錯清單裡分辨這筆是不是雲端救回來的。失敗(`nil`)則維持原本行為,不疊字。

## 刻意沒做的事

- 沒把這個 fallback 接到「整頁對位」路線(`vlmEngine.translatePage` 那一段)——那段本來就是「對不到就退回逐塊」,不會走到「最終失敗」這個狀態,不需要這層保險
- 沒有做快取(同一句話翻兩次會打兩次 Google)——目前一頁漫畫的失敗區塊數量很小,先不做,之後如果 Cyril 反應很多重複詞才考慮
- 沒有把「這筆是不是雲端翻的」單獨用顏色/圖示標在疊字本身上(只在展開的除錯明細看得到來源)——如果 Cyril 想在畫面上直接看出來哪些是 Google 救的,之後再加

## 下次裝機要驗證的重點

1. 找一個已知本機模型會卡死/照抄的區塊(例如先前 `VAMONOS.`、生成迴圈卡死那種),確認除錯明細「來源」變成「逐塊,Google 翻譯備援」,而且顯示出來的譯文是真的翻譯內容,不是原文照抄
2. 確認正常翻得出來的區塊完全不受影響——這是純新增的 fallback 分支,只在既有失敗路徑之後才觸發,理論上不會動到任何已經翻對的結果,但仍要照方法論裝機驗證,不能省略
3. 留意這個免費端點會不會被偶發性擋掉(例如回傳非 200,或格式跟預期不同解析不出來)——目前的處理是「解析不出來就當作這條路也失敗」,不會顯示錯誤譯文,但如果常態性擋掉,除錯明細會一路都是失敗訊息,那時要考慮要不要換成官方付費 API 或加重試

# 圖片偵測時機:提早偵測被 isCandidate 尺寸門檻抵銷

## 問題

Cyril 回報:目前要捲到圖片底部才會開始下載+翻譯,不是一看到圖片就開始——理論上 `PageBridge.swift` 的 `IntersectionObserver` 已經用 `rootMargin: '0px 0px 200% 0px'` 提早 2 個螢幕高度偵測,應該老早就該觸發。

## 判讀

`isCandidate(img)` 原本只看 `getBoundingClientRect()`(瀏覽器目前實際渲染出來的尺寸)。如果站方的 lazy-load 圖片在真正換上 `src` 之前,版面沒有用 CSS `aspect-ratio` 或 HTML `width`/`height` 屬性保留版位(而是用小尺寸/未定型的佔位元素撐著),我們的 `IntersectionObserver` 提早觸發時 `rect` 還是 0 或很小,`isCandidate` 判定失敗、不回報;要等到站方自己的 lazy-load 邏輯換好 `src`,我們的 `MutationObserver` 重新檢查才會過關——但站方自己的觸發門檻通常比我們窄很多(甚至就是「快進入視窗」才換),等於我們刻意放大的 200% 提前量被這個尺寸門檻整個抵銷掉,實際效果變成「跟著站方的節奏走」。

另外 `currentSrc(img)` 原本只認 `data-src` 一種 lazy-load 屬性名稱,其他常見命名(`data-original`、`data-lazy-src`、`data-lazy`)完全抓不到,如果站方用的是這些命名,我們在 src 真正換好前完全拿不到任何網址可用。

## 修法(這輪先試,還沒裝機驗證)

- `isCandidate`:改成優先看 HTML 上明確宣告的 `width`/`height` 屬性(多數會保留版位的站在圖片還沒載入時就先寫好這個),量不到才退回實際渲染尺寸——這樣即使視覺上還是佔位圖,只要版位尺寸已知就能提早通過判定
- `currentSrc`:多加幾個常見 lazy-load 屬性名稱的 fallback(`data-original`/`data-lazy-src`/`data-lazy`)

## 已知限制,如果這輪還是沒改善

如果目標站是用「虛擬捲動」(`<img>` 節點本身要捲到夠近才會被插進 DOM,不是已經在 DOM 裡只是屬性沒換好)——這種情況下我們的 `MutationObserver`/`IntersectionObserver` 都無能為力,因為在節點真的被插入之前,我們根本沒有東西可以觀察,只能跟著站方自己插入 DOM 的時機走。真的遇到這種情況,需要 Cyril 提供實際測試網址讓下一輪針對那個站的 DOM 結構討論其他做法(例如觀察站方自己的骨架佔位元素)。

## 裝機驗證要看

用 Cyril 平常測試的漫畫網址重跑一次,捲動頁面時觀察除錯清單:圖片項目出現「🔍 偵測到」→「下載中」的時間點,有沒有明顯提前到「肉眼還沒捲到那張圖」的階段,而不是像現在這樣要捲到圖片底部才出現。

# 邊捲邊翻改成「整話先翻完再看」(品質優先)

## 為什麼放棄邊捲邊翻

實際抓 `https://olympusxyz.com/capitulo/131734/...` 這個測試網址的 HTML 來看才發現:這個站的 `<img>` 標籤 `src` 從伺服器端渲染就已經是正確的最終網址(沒有 `data-src` 換源這回事,靠瀏覽器原生 `loading="lazy"`),代表偵測本身應該早就沒問題——真正的瓶頸是**翻譯處理速度天生跟不上正常捲動速度**:VLM 推理是單一序列(一次只能跑一個),一張圖好幾個對話框、每個區塊數秒起跳(還有這次剛加的最多 3 次重試+ Google 翻譯備援,失敗時更久),絕不可能跟 Safari 那種「純文字替換」比快。

跟 Cyril 討論後確認一個關鍵事實:**Safari 在這類站上能即時疊字翻譯,其實也是先用系統 OCR(跟我們用的 Vision 同一顆引擎)抓字再翻——它翻得快是因為它完全沒有 VLM 這個步驟**,代價正是翻譯品質差(手寫體常認錯字,我們先前踩過的「UWA 被認成 LIWA」就是同一個病)。我們當初加 VLM 就是為了解決 Safari 這種做法的品質問題,所以「跟 Safari 一樣快」在保留 VLM 品質的前提下做不到,只能兩者選一:要嘛接受「先出草稿、之後悄悄變好」的畫面跳動感,要嘛「先等全部翻完、之後全程流暢」。**Cyril 選了後者:追求翻譯品質。**

## 修法

- `PageBridge.swift`:新增 `window.imgTranslateReportAll()`,無視目前捲動位置與 `IntersectionObserver` 的交集狀態,直接把「現在 DOM 裡找得到的所有候選圖片」全部呼叫 `report()`,回傳這次總共回報了幾張
- `TranslationRequestCoordinator.swift`:新增 `startPreTranslateAll()`(呼叫上面那個 JS 函式,設定 `isPreTranslating = true`)、`skipPreTranslateWait()`(使用者不想等,直接拿掉遮罩,已經排隊的工作不取消,背景繼續跑)、`checkPreTranslateCompletion()`(掛在 `updateStatus` 上,每次任何一張圖狀態改變就檢查一次「是否全部圖片都已經是`已翻譯`/`沒文字`/`失敗`這種定案狀態」,是的話自動解除遮罩)
- `MangaReaderView.swift`:網址列下方加「翻譯整話」按鈕;`MangaWebView` 外面包一層 `ZStack`,`isPreTranslating` 為真時蓋上進度遮罩(`ProgressView` + 「翻譯整話中 N/總數」+ 一顆「先看已翻好的部分」提前解除遮罩的按鈕)

## 刻意沒做的事

- 沒有拿掉既有的「邊捲邊翻」機制(`IntersectionObserver` 提前偵測那套)——兩者不衝突,`handleDetectedImage` 本來就有 `indexByURL[url] == nil` 防重複,整話翻完之後如果站方又動態插入新圖(無限捲動),舊機制還能接手處理
- 沒有處理「虛擬捲動」站(圖片節點要捲到夠近才插入 DOM)——這個模式的前提是「章節所有圖片一開始就都在 DOM 裡」,目前測試站符合,如果之後換一個用虛擬捲動的站,這個模式在使用者開始捲動前找不到後面的圖,`imgTranslateReportAll` 只能回報看得到的那些,需要另外討論
- 沒有做「取消已排隊的翻譯工作」——按「先看已翻好的部分」只是拿掉遮罩,VLM 還是會把已經排進佇列的圖跑完,不會平白浪費掉已經開始的推理

## 裝機驗證要看

1. 貼網址進去、等頁面載入完成,按「翻譯整話」,確認遮罩出現、進度數字有跑(「翻譯整話中 N/總數」)
2. 全部跑完後遮罩自動消失,直接開始捲動,確認**每張圖一出現就已經是翻譯完成的狀態**,不會再看到「翻譯中」或空白疊字
3. 按「先看已翻好的部分」提前跳過,確認畫面能正常捲動,已經翻完的圖有疊字、還沒翻完的圖之後捲到會自動補上(邊捲邊翻的後備行為)
4. 留意整話翻完實際花多久時間(這頁 19+ 張圖,如果平均每張要處理好幾個區塊,總時間可能長達數分鐘),回報實際等待時間,評估這個模式的等待成本是否可以接受
