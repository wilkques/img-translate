# ImgTranslate POC — OCR + 原地疊字翻譯

## 這支 App 在驗什麼

目標效果:`/var/www/try/1.jpg`(原文)→ `/var/www/try/2.jpg`(翻譯後)——**原地蓋掉原文位置、換上翻譯**,不是加字幕。

這支 App 是驗證這個 rendering pipeline 本身走不走得通,用內建的固定測試圖(`Fixtures/sample-es.jpg`,已裁掉手機狀態列/Safari 網址列,只留漫畫內容)。**不含**即時擷取網頁圖片的部分(WKWebView 整合是下一階段)。

流程:App 開啟 → 自動對內建測試圖跑 Vision OCR(抓文字+座標)→ 把辨識到的文字丟給本機 MLX 模型翻譯(見下方)→ 依座標畫遮色框蓋住原文、疊上譯文。畫面上方有語言選單(來源/目標),選好會自動重跑一次;預設西班牙文 → 繁體中文(配合測試圖)。畫面下方有除錯清單顯示「Vision 實際辨識出的原文」,方便判斷效果不對時是辨識錯還是翻譯錯。按鈕可以切換顯示原圖 / 疊字後的畫面,直接跟 `2.jpg` 比對。

## 語言選擇

目前選單提供:西班牙文、英文、日文、韓文、法文、德文、簡體中文、繁體中文(台灣)。這是固定清單,對應 `LocalLLMTranslationEngine.languageNameMap` 有映射的語言。測試圖本身是西班牙文,選別的來源語言時 Vision 辨識會不準是正常的(圖片內容沒變,只是叫辨識器用別種語言的字型規則去猜)。

1. 打開 App,等它自動跑完 OCR + 翻譯(畫面上的「狀態」文字會顯示進度)
2. **先看畫面下方的除錯清單**——每一行是「原文 → 譯文」,檢查 Vision 有沒有把 `¡¡¡GRRRRRRAAAAGH!!!!` 這種狀聲詞、`YA BASTA...` 這種手寫感粗體字正確辨識出來

4. 按底部按鈕切換「顯示原圖」,確認原圖本身正常顯示(排除是圖片本身載入失敗的問題)

## MLX 本機模型翻譯(Stage 2)

真正接上模型:`mlx-community/translategemma-4b-it-4bit_immersive-translate`(TranslateGemma 4B 翻譯專用微調,重新包過 chat template 給一般推理引擎用)。這是唯一的翻譯引擎,不再有系統翻譯選項。

⚠️ **中途踩過一個坑**:TranslateGemma 官方 chat template 要求結構化 content 格式,不吃我們原本用的 `additionalContext` 塞法,實測會直接 `Jinja.TemplateException`。已改用 `_immersive-translate` 這個變體版本,語言資訊改用純文字分隔符號包在 prompt 裡送(`<<<source>>>English<<<target>>>Chinese (Traditional)<<<text>>>原文`),不再需要結構化 content。

**首次使用流程**:
1. 打開 App
2. **務必連 WiFi**——首次會自動下載約 2.2GB 的模型檔案到 `Application Support`(不是 Caches,不會被系統清掉),下載進度條會顯示在語言選單下方
3. 下載完成後短暫「載入模型權重中…」
4. 之後才開始逐句翻譯,顯示「本機模型翻譯中 N/總數」
5. 全部完成後套用到疊字畫面,跟 `/var/www/try/2.jpg` 比對

**這是完全沒驗過的環節**,重點觀察並回報:
- 下載進度條有沒有正常跑、卡在多少 % 或直接失敗
- 下載完成後載入權重要等多久
- 實際跑一句翻譯要等幾秒(推理速度)
- 過程中 App 有沒有被系統強制關閉(記憶體問題——雖然 `lc-memprobe` 驗過 entitlement 開了約 6GB,但那是純記憶體佔用測試,沒有實際跑 GPU 推理)
- 翻譯出來的中文品質,跟你印象中 Locally AI 的翻譯品質比較

**已知的技術細節**:
- 模型下載到 LiveContainer 的 App 專屬 container,重新裝新版 ipa **不會**清掉已下載的模型(除非在 LiveContainer 對這個 App 執行 Delete Data/Remove Container),之後改程式碼重新 push 不用每次重下 2.2GB
- 語言選單的代碼(如 `zh-Hant-TW`)已經在程式碼裡映射成模板要的完整英文語言名稱(如 "Chinese (Traditional)"),其他語言選項也都有映射,理論上都能用

## 疊字效果調整(Stage 2 後續)

裝機實測翻譯正確(跟另外用 Gemma/Qwen 跑同一段文字三方比對,語意沒問題,順序比多模態直讀圖片穩定),但抓到三個要調的地方:

1. **狀聲詞翻譯風格**:吼叫聲(`GRRRAAAGH` 這種)原本會被翻成「怒吼」這類描述詞,不是漫畫常見的擬聲字轉寫(如「啊啊啊啊」)。加了一個簡單偵測(文字裡有沒有連續 3 個以上相同字母,語言無關的判斷法),命中的話在送給模型的內容前面加一句英文提示,要求音譯不要翻譯字義。**這是實驗性做法**,能不能被模型正確理解、還是被當成內容一起翻出來,需要裝機驗證
2. **遮色框太小、字被壓得很小**:Vision 抓的原文 bbox 只框住文字墨跡本身,比整顆手繪對話框小很多,原本照原始尺寸畫框導致 `minimumScaleFactor` 把字壓得很小。已經把框往外撐大 35%(中心點不變)、`minimumScaleFactor` 下限從 0.3 調到 0.5、起始字級從框高 45% 調到撐大後框高的 60%
3. **字體風格**:原本用系統圓潤字重(`.rounded design`),改成 `.default design` 的 `.heavy` 粗細,iOS 內建字體裡最接近漫畫感的選項(不是真正的漫畫字體,要用真正的漫畫字體需要額外提供 `.ttf`/`.otf` 字體檔案並注意商用授權)

三項都還沒裝機驗證,尤其第 1 項風險最高。跑完把畫面截圖回報。

**後續兩輪修正**:
- 狀聲詞音譯提示第一版實測會被模型當內容一起吐出來(輸出裡混進「(模擬聲音:...)」這種說明文字)。改法:提示語改更強硬要求「只輸出結果、不要輸出說明」,並在輸出後加一道保險過濾(`stripLeakedInstruction`)偵測開頭括號說明並砍掉
- 跟 Qwen 三方比對後,發現 TranslateGemma 預設語氣偏書面正式(「你很吵」),Qwen 更口語生動(「你吵死了」)。嘗試加一句語氣提示(要求口語自然、像漫畫台詞)——**裝機實測翻車**:同樣是溫度 0 貪婪解碼(非隨機),`YA BASTA...` 穩定翻成土耳其文而不是繁體中文,語言整個跑掉。判定這個提示對 TranslateGemma(窄用途翻譯微調模型)太不穩定,**已經退掉**,一般對話恢復不加任何提示,正確性優先於語氣潤飾。狀聲詞音譯提示裝機測過乾淨、語言正確,保留
- 頂部對話框兩行字(`¡UWA! ¡¡UWAA!!` / `¡¡UWAAA!!!!`)被 Vision 拆成兩塊相鄰 bbox,原本高度也撐大 35% 導致上下兩塊疊在一起。改寬高不對稱撐大(寬 50%/高 10%)後裝機測還是會疊——兩塊 bbox 原本間距就很近,連 10% 都撐不住,**改成高度完全不撐**,只撐寬度

**第三輪修正**(裝機驗證上面兩輪的結果):語言錯誤確認修好(`YA BASTA...` 恢復翻成繁中),但抓到新的漏網之魚——OCR 把 `¡UWA! ¡¡UWAA!!` 認錯成 `¡LIWA! ¡¡LWAA!!`,重複字母被吃掉導致狀聲詞偵測沒觸發,被當一般文字翻成「離亞!離亞!」(像人名音譯)。修法:狀聲詞偵測加一個西班牙文專屬判準——文字含倒驚嘆號「¡」就視為喊叫聲,不用依賴字母重複,OCR 認錯字母也不影響判斷(代價:真的用「¡...!」喊出來的一般單字也會被誤判成狀聲詞,這次測試資料沒有這種情況,先接受)。疊字重疊改成高度完全不撐,只撐寬度

**第四輪修正(結構性)**:裝機驗證第三輪,狀聲詞判準有效(不再被當人名翻),但頂部兩行字疊在一起的問題還在——不管怎麼調撐大倍率都治標不治本,因為兩個各自獨立的遮色框只要間距夠近,調整尺寸永遠有機率再疊回去。改成**結構性修法**:把撐大後會碰撞的相鄰文字框直接合併成一個(而不是各自畫框再閃避碰撞),合併後的框裡放多行文字,只疊一個乾淨的遮色框。同時字級調小(起始字級乘數 0.6→0.4、縮字下限 0.5→0.4、`lineLimit` 3→4 容納合併後的多行文字)。

技術細節:`CoordinateTransform` 拆成兩段(Vision 正規化座標→圖片像素座標、圖片像素座標→畫面座標),合併判斷在像素座標空間做(不受畫面尺寸影響,穩定),合併用的撐大倍率(寬 1.5/高 1.0)刻意跟 `BubbleOverlayView` 實際畫框的倍率保持一致,不然合併決策跟畫出來的框會對不上。

裝機驗證第四輪:疊字重疊確認解決,但頂部那句(`¡UWA! ¡¡UWAA!!`)翻出來還是跟另外用 Gemma4/Qwen3.5 跑的結果不一樣——查證後發現問題不在翻譯,是**更前面的 OCR 就已經認錯字**:Vision 把 `¡UWA! ¡¡UWAA!!` 認成 `¡LIWA! ¡¡LWAA!!`(多兩個 L),音譯模型是照著這個已經錯誤的原文去做,翻成「離哇」而不是「哇」。Cyril 用手機上的 Locally AI(Qwen3.5、Gemma4)直接讀同一張圖,兩個都正確讀出「UWA」——證實多模態模型讀圖在這種手寫粗體字上比 Apple Vision OCR 準,但代價是沒有座標,不能直接拿來做「原地回填」。

## 混合式架構:Vision 抓位置 + VLM 讀圖翻譯

因為最終產品是「輸入漫畫網址、對網頁 `<img src>` 做翻譯回填」,回填一定要座標,所以改成混合式,而不是整個換成整張圖丟給多模態模型(那樣會失去座標):

- **位置**:繼續用 Vision OCR 的 boundingBox
- **文字內容**:不信任 Vision 辨識出的文字,改成把 bbox 對應的區域從原圖裁一小塊,丟給支援讀圖的 MLX 視覺語言模型(VLM)讀字+直接翻譯,一次搞定(不再另外接純文字翻譯模型,兩個模型同時載入記憶體太緊)

模型:`lmstudio-community/Qwen3-VL-4B-Instruct-MLX-4bit`(3.09GB,4-bit,`VLMRegistry` 內建 preset)。選它不選 Gemma 3 多模態版的原因:Gemma3 的 processor 固定用 896×896 跑滿整個 vision tower,不管裁圖多小都是同樣重的運算;Qwen3-VL 是動態解析度,小裁圖只吃對應比例的 token,對「每塊裁圖各跑一次推理」這個用法是數量級的速度差異。

**畫面上新增「翻譯引擎」切換**(視覺模型 VLM / 文字模型 OCR+TranslateGemma),可以在同一張圖上直接對照兩條路線。兩個模型不能同時載入(2.2GB+3.1GB 太緊),切換引擎時會自動卸載沒在用的那個。

**除錯清單改成裁圖縮圖 + 三欄對照**(Vision 辨識原文 / VLM 讀到的原文 / 譯文):多了裁圖這個環節,失敗模式從「辨識錯/翻譯錯」兩種變成「框抓錯/裁歪裁太緊/VLM讀錯/翻錯」四種,沒有縮圖對照沒辦法定位問題出在哪一步,這是這次投資報酬率最高的一塊。

**合併邏輯從畫面層前移到 OCR 階段**:原本(前四輪)是先各自畫框、疊字時才合併;這次改成 OCR 完成後立刻合併,合併後才裁圖、才呼叫 VLM——好處是 VLM 呼叫次數少一半以上(一顆對話框從好幾次變一次)、VLM 能看到完整語句上下文而不是被切成片段。

**裁圖要往外擴邊**(不能照 Vision 緊貼的 bbox 裁):粗體描邊/筆畫尾巴常常超出框,裁太緊等於把「Vision 認錯」換成「VLM 看不到」。橫向擴 8%、縱向擴 20%(縱向擴多一點,但因為已經先合併過同一對話框的多行,不會吃到隔壁真正不相干的文字)。

**首次使用流程**(VLM 引擎):
1. 語言選單下方切到「視覺模型(VLM 讀圖)」(預設就是)
2. 連 WiFi,首次下載約 3.1GB
3. 下載完成後「載入模型權重中…」→「首次暖機中(編譯 Metal pipeline)…」(用假圖跑一次墊底,避免第一個對話框背暖機延遲的鍋)
4. 逐塊裁圖+讀字+翻譯,每塊約 2-4 秒,即時更新畫面,不用等全部做完
5. 完成後看除錯清單的縮圖 + 三欄對照,尤其是先前認錯的 `¡UWA! ¡¡UWAA!!` 那段有沒有被 VLM 正確讀出來

**已知風險,還沒裝機驗證**:
- 速度估算(每塊 2-4 秒、一頁合併後 3-6 塊約 10-25 秒)是理論值,需要實測校正
- 記憶體峰值估算約 3.5-4.0GB,6GB 上限內有餘裕,但沒驗過裝置實際壓力
- 裁圖擴邊比例(橫 8%/縱 20%)是起手值,需要用縮圖實際校正
- 結構性上限:如果 Vision 對某段風格化文字完全沒偵測到 bbox,VLM 永遠看不到它,要檢查 `blocks.count` 有沒有涵蓋畫面上肉眼看到的所有文字
- prompt 裡直接寫狀聲詞音譯指示(不是像 TranslateGemma 那次額外塞一句獨立提示):Qwen3-VL 是通用 instruct 模型,理論上比窄用途翻譯微調模型更吃得住多步驟指令,但沒裝機驗證過,如果輸出語言跑掉,先把 prompt 簡化

**裝機驗證**:`YA BASTA...`/`ERES RUIDOSO..` 這兩句 VLM 讀字正確、翻譯合理(「好了,夠了...」「你是吵鬧的...」),證實混合式架構的核心假設成立。但抓到一個新問題——**貪婪解碼(temperature 0)在難讀的裁圖上會卡進生成迴圈**:頂部那句(`¡UWA! ¡¡UWAA!!`)跟最後的吼叫聲那格,VLM 輸出變成一長串同一個字元不斷重複(例如整段都是 "iiiii..."),燒光 maxTokens 也生不出正常的 ORIGINAL/TRANSLATION 格式。

修法:temperature 從 0 調到 0.2(降低卡迴圈機率,翻譯還是接近穩定,不追求創意)、maxTokens 從 128 降到 80(萬一還是卡迴圈,少燒一點時間)、`parse()` 加一道退化輸出偵測(同一個非空白字元連續重複超過 12 次就判定生成失敗,回傳明確的「[生成失敗:輸出異常重複]」而不是把垃圾文字顯示出來)。

**裝機驗證(第二次)**:退化偵測生效了——頂部那句這次正確顯示「[生成失敗:輸出異常重複]」,不會再顯示一長串垃圾字元。但發現另一個不同的失敗模式:最後那格(合併過兩行的吼叫聲對話框)VLM 只讀完 Step 1(複誦原文)就停住,沒有寫到 Step 2 的翻譯,輸出被截斷在「ORIGINAL:...」——不是字元重複(退化偵測抓不到這種)。判斷是 maxTokens 80 對「合併過多行、內容比較長」的框太緊,模型複誦原文就吃掉大半額度。既然退化偵測已經頂住了真正的無限迴圈,把 maxTokens 拉回到 150 給多行框多一點空間,這輪還沒裝機驗證。

**裝機驗證(第三次)**:maxTokens 拉回 150 後,截斷問題確認解決——最後那格(合併過的吼叫聲對話框)不再卡在「只複誦完 Step 1」,但生成本身還是卡進重複迴圈,被退化偵測抓到,乾淨顯示「[生成失敗:輸出異常重複]」(不再是截斷的半成品)。頂部 `¡UWA! ¡¡UWAA!!` 那格也是同樣結果。兩句正常句子(`YA BASTA...`/`ERES RUIDOSO..`)維持翻對。

判讀:目前卡迴圈的兩塊有共通點——**來源文字本身就是大量重複字母**(`UWAAA`、`GRRRRRRAAAAGH`)。Prompt 的 Step 1 要求逐字複誦這種輸入,等於在提示模型「接下來繼續重複同一個字」,對這類 OOD 輸入特別容易觸發生成迴圈。不想把常駐 temperature 整體拉高(會犧牲另外兩句已經穩定翻對句子的穩定性),改成**只在偵測到退化輸出時,原地重試一次、用更高溫度(0.7)打散貪婪路徑**,只有卡迴圈的少數難字才付重試的代價。這輪還沒裝機驗證。

**裝機驗證(第四次)**:重試機制上線後,頂部區塊重試後仍然完全失敗(退化偵測依舊命中)。底部合併區塊這次沒有卡進字元重複迴圈,但輸出還是只複誦完原文就停住,沒有寫到 `TRANSLATION:`,`parse()` 抓不到就把整段未完成輸出當譯文顯示,畫面上譯文欄變成一串 `ORIGINAL:...` 的原始文字,是明顯錯誤的顯示結果。判斷「Step 1 要求逐字精確複誦」是根因,把該指示放寬成「重複字母寫 2-4 次自然量就好,不用精確計數」。這輪還沒裝機驗證。

**裝機驗證(第五次)**:結果幾乎沒變——頂部區塊依然完全退化失敗;底部合併區塊這次 `VLM讀到` 抓到完整兩段原文,但譯文欄還是顯示未完成的 `ORIGINAL:...` 輸出,代表還是沒寫到 `TRANSLATION:`。**修正診斷**:上一輪判斷「措辭要求精確複誦」是根因,證明不是(或不是全部)——真正的結構性問題是**順序**:prompt 要求先寫 Step 1(讀原文)才寫 Step 2(翻譯),只要模型在複誦原文階段卡住或耗光額度,排在後面的翻譯永遠生不出來,跟措辭怎麼放寬無關。修法:**把輸出順序整個對調**,Step 1 改成先要求 `TRANSLATION`,Step 2 才是 `ORIGINAL`(僅供除錯參考)——這樣即使模型在寫原文時卡住,真正需要的譯文已經先寫出來了。`parse()` 本來就是逐行找標籤、不假設順序,不用改動。這輪還沒裝機驗證。

**裝機驗證(第六次)**:**這次改動是負分**。頂部區塊這次總算把原文讀對了(`¡UWA! ¡¡UWA!! ¡¡¡UWAAA!!!`,不再是 Vision 認錯的 LIWA),證實 VLM 讀圖本身沒問題,但 `TRANSLATION` 欄卻原封不動照抄原文,完全沒有翻譯動作。更嚴重的是連續五輪都穩定翻對的 `YA BASTA...`/`ERES RUIDOSO..` 這次也被搞壞——前者輸出被截斷成 `TRANSLA...`,後者譯文欄混進原文黏成一團。判讀:先讀原文再翻譯這個「兩步驟」本身在幫一般句子維持翻譯品質,問題只出在兩個重複字母極端多的難字上,不該為了救這兩個難字動到對所有區塊都生效的主要 prompt。

修法:**改回原本驗證過穩定的 ORIGINAL→TRANSLATION 順序**(等於還原第四次之前的版本),兩個難字改交給 retry 階段一個**完全不同、更簡化**的 prompt 處理——retry prompt 直接拿掉「逐字讀出原文」這一步(那正是卡迴圈的根源),只要求「給一個自然的音譯,不用對照原文」,只輸出一行 `TRANSLATION:`。主要 prompt 完全不受影響,只有退化偵測命中才會換到這個 retry prompt。這輪還沒裝機驗證。
